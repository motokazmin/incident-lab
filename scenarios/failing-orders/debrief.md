# Разбор: «Часть заказов падает»

## Что случилось

Чтобы оформить заказ, `placeOrder` в одной транзакции списывает товары со склада: по одному `UPDATE` на позицию, в том порядке, в каком покупатель клал их в корзину. Строка товара, которую обновил `UPDATE`, остаётся заблокированной до конца транзакции (до `COMMIT` или отката). Корзины у людей разные: один добавил товар 2, потом 3, другой — наоборот. Пока такие заказы оформляются по одному, всё работает. Если два из них идут одновременно, получается круг: первый держит товар 2 и ждёт товар 3, второй держит 3 и ждёт 2. Это взаимная блокировка, дедлок (deadlock). Выхода из неё нет, и через `deadlock_timeout` (здесь 200 мс) PostgreSQL обрывает одну из транзакций с ошибкой `deadlock detected`. Сервис отвечает клиенту 500.

Код был таким всегда. Сегодня магазин разослал пуш «Повтори заказ», и клиенты жмут кнопку разом: каждые 10 с по 16 повторов в одну секунду поверх обычного потока. Встречные заказы с общими товарами начали идти одновременно, поэтому ошибки приходят волнами после каждой рассылки, а между ними тихо. Со второй попытки заказ проходит, потому что второй раз встречи уже нет.

Починка: брать блокировки в одном порядке для всех заказов. Это делает сортировка позиций по `product_id` в одном месте, в `placeOrder`.

## Что сломано в коде

`orders.go`:

```go
func (s *server) orderItems(orderID int64) ([]item, error) {
    rows, err := s.db.Query(`SELECT product_id, qty FROM order_items WHERE order_id = $1 ORDER BY position`, orderID) // ①
    ...
}

func (s *server) placeOrder(customer int, items []item) (int64, error) {
    tx, err := s.db.Begin()
    ...
    for i, it := range items {                                                                 // ②
        var price int
        err := tx.QueryRow(`UPDATE products SET stock = stock - $1 WHERE id = $2 AND stock >= $1 RETURNING price`, it.Qty, it.ProductID).Scan(&price) // ③
        ...
        // Постоянному покупателю товара — скидка 5%.
        var bought int
        if err := tx.QueryRow(`SELECT count(*) FROM order_items i JOIN orders o ON o.id = i.order_id WHERE o.customer_id = $1 AND i.product_id = $2`, customer, it.ProductID).Scan(&bought); err != nil { // ④
            return 0, fmt.Errorf("скидка %d: %w", it.ProductID, err)
        }
        ...
    }
    ...
    return orderID, tx.Commit()                                                                // ⑤
}
```

① позиции читаются в порядке корзины; ② блокировки берутся в том же порядке; ③ строка товара заблокирована до конца транзакции; ④ ещё один запрос, пока блокировка держится; ⑤ блокировки снимаются только здесь.

По отдельности каждая строка разумна. `ORDER BY position` ① показывает заказ так, как его собирал покупатель. Условие `stock >= $1` в `UPDATE` ③ отличает «раскуплено» (ответ 409) от ошибки. Одна транзакция ⑤ нужна, чтобы заказ либо оформился целиком, либо не оформился совсем. Скидка ④ выглядит безобидно, но она считает историю покупателя и делает транзакцию заметно длиннее, а блокировка товара ③ всё это время удержана. Порядок ② приходит из двух мест: из истории заказа (`repeatOrder`) и из тела `POST /orders` (`createOrder`), и в обоих случаях задаёт его покупатель, а не код. Под распродажей идут повторы, но второй источник тот же. Поломка возникает из сочетания ② и ③: блокировки берутся в разном порядке и держатся долго.

## Как это находится

Каждый шаг отвечает на один вопрос. В скобках указана ступень подсказок, которая ведёт к тому же шагу.

**1. Сервис упал или ошибки идут только временами?** (подсказка «Что говорят графики»)
```
svc status
```
Сервис запущен, перезапусков нет. А на графике ошибки идут всплесками после рассылки, между ними тихо. Значит, процесс жив, а сбой зависит от одновременности запросов.

**2. Что говорит сам сервис?** (подсказка «Что в логах»)
```
svc logs
```
Останови вывод через Ctrl+C. Красные строки `status=500` — это `POST /orders/…/repeat`. Над каждой жирная строка самого сервиса: `repeatOrder: товар N: pq: deadlock detected`. Ошибку сервису вернула база, а не его собственный код.

**3. Кто кого ждёт?** (подсказка «Что пишет база»)
```
grep -A20 'deadlock detected' /var/log/postgresql.log | tail -n 40
```
В `DETAIL` процессы ждут друг друга по кругу: каждый `waits for ShareLock on transaction` следующего, а последний — первого. Это и есть цикл: A ждёт B, а B ждёт A. В залпе в круге бывает и больше двух процессов. Все запросы в круге — `UPDATE products ...`, то есть ждут они строки товаров.

**4. Это случайность или повторяется?** (подсказка «Сколько их»)
```
psql -U postgres -d shop -c "select deadlocks from pg_stat_database where datname='shop'"
```
Выполни несколько раз подряд. Счётчик, который ведёт сама база, растёт: дедлоки идут постоянно, а не один раз.

**5. На каких товарах и у каких заказов?** (подсказка «Какие товары»)
```
curl localhost:8080/orders/1; echo; curl localhost:8080/orders/5
```
В журнале из шага 3 в строке `CONTEXT` есть `parameters`, где `$2` — товар, и тот же номер стоит в `svc logs` после слова «товар». Заказы 1 и 5 содержат одни и те же товары 2 и 3, но в `items` они идут в разном порядке. Такая пара и образует цикл.

**6. Откуда берётся порядок?** (подсказка «Где порядок») Открой `orders.go`. `orderItems` берёт позиции по `position`, а `placeOrder` блокирует в этом же порядке. В `createOrder` порядок приходит из тела запроса. Значит, чинить надо там, где блокировки берутся, а не там, где порядок читается.

**7. Почему это началось сегодня?** Сам код не менялся. Раньше повторы заказов шли редко и по одному, поэтому две встречные транзакции почти не пересекались во времени. Пуш «Повтори заказ» сделал их одновременными. Причина в порядке блокировок, рассылка её только вскрыла.

## Как чинить

Все транзакции должны брать одни и те же блокировки в одном порядке.

- **Быстро:** в начале `placeOrder` отсортировать копию позиций по `product_id`. Работает для заказов из любого источника, истории и API. Оговорка: в новом заказе `position` сохраняется уже в отсортированном порядке, исходный порядок корзины теряется. Если он нужен для показа, храни его отдельным полем.
- **Эталон:** та же сортировка как единственное место, где задаётся порядок блокировок, и повтор при `40P01` вторым слоем: в проде дедлок возможен и с другими таблицами, а повтор поверх верного порядка срабатывает редко и ничего не прячет.

```go
// orders.go, начало placeOrder; добавь "slices" в импорт
items = slices.Clone(items)
slices.SortFunc(items, func(a, b item) int { return a.ProductID - b.ProductID })
```

Потом сохрани файл, выполни `svc deploy` и нажми «Проверить починку». Другие верные варианты, вроде `SELECT ... WHERE id = ANY($1) ORDER BY id FOR UPDATE` в начале транзакции, — в блоке «Все починки».

## Почему очевидные «починки» не работают

Проверка смотрит на поведение системы, а не на текст правки: счётчик дедлоков в базе, номера заказов, остатки.

- **Рестарт и повтор при ошибке:** рестарт не меняет порядок блокировок. Повтор прячет ошибку от клиента, но цикл в базе остаётся: каждая жертва ждёт `deadlock_timeout`, потом делает всю работу заново. Счётчик `deadlocks` растёт.
- **`lock_timeout` с повтором или точкой сохранения:** ожидание обрывается раньше, чем база ищет цикл, и дедлоков в счётчике нет. Но работа делается дважды: с повтором транзакции откатываются и в номерах заказов появляются дыры, с точкой сохранения строки товаров обновляются больше раза на позицию.
- **Настройки `deadlock_timeout`:** короткий срок только быстрее находит те же циклы. Огромный отключает поиск: транзакции из цикла висят в базе и держат соединения. Обёртка HTTP через 1 с отвечает клиенту 503, но транзакцию не отменяет (`Begin` без контекста), пул забивается, и падают даже чтения.
- **Правка порядка только в одном месте:** `ORDER BY product_id` в выборке или сортировка в `createOrder` лечит один из двух источников. Второй продолжает приходить во встречном порядке.
- **Индекс под скидку:** транзакция становится короче, и встречи реже. Порядок блокировок прежний, поэтому в залпе одновременных заказов цикл всё равно возникает.
- **Убрать транзакцию:** блокировки не держатся, но при отказе по раскупленному товару позиции перед ним уже списаны и не откатываются.
- **Убрать `AND stock >= $1`:** заказ с раскупленным товаром упирается в `CHECK (stock >= 0)` схемы и получает 500 вместо 409. Дедлок это само по себе не убирает.
- **Читать остаток и писать значением:** две транзакции читают остаток 1 и обе пишут 0, последнюю единицу покупают несколько человек.

## Правило на будущее

> Ошибки волнами при живом сервисе → что пишет база → кто кого ждёт и на каких строках → у двух транзакций разный порядок одних и тех же блокировок.
> «Повторить при ошибке» ≠ «убрать цикл»: порядок блокировок должен быть один для всех.

<summary>Механика по звеньям: от строки кода до ошибки клиента</summary>

1. Приходит залп: 16 `POST /orders/{id}/repeat` в одну секунду поверх фона. Для каждого сервис читает заказ из истории и позиции в порядке `position` (①).
2. Транзакция A делает `UPDATE` товара 2, транзакция B — товара 3. Каждая теперь держит свою строку (③).
3. Обе считают скидку (④) и идут к следующей позиции. A хочет строку 3, но она заблокирована B, и A ждёт, пока B закончит транзакцию. В журнале это `waits for ShareLock on transaction`. B так же ждёт A.
4. Никто из них не может продолжить, потому что освободить строку можно только завершив транзакцию (⑤).
5. Через `deadlock_timeout` (200 мс) ожидающий процесс запускает проверку цикла. База находит цикл и откатывает одну транзакцию с кодом `40P01`.
6. Драйвер возвращает `pq: deadlock detected`, обработчик пишет `repeatOrder: товар N: ...` и отвечает 500. Вторая транзакция продолжает и завершается.
7. Пока транзакции ждут, каждая занимает одно из 15 соединений пула. Часть повторов в залпе не укладывается в 1 с — ждёт строку или соединение — и `TimeoutHandler` отвечает 503. Чтения при этом проходят: на стенде все 503 пришлись на повторы, у `GET` их нет. Волна закончилась — пул снова свободен.
8. Клиент повторяет нажатие. Остальных встречных заказов в этот момент уже нет, и заказ проходит.

2026-11-09 21:23:06.507 UTC [344] DETAIL:  Process 344 waits for ShareLock on transaction 1594; blocked by process 338.

Читай `DETAIL` как цепочку: 344 ждёт транзакцию 1594, которую ведёт 338, а 338 ждёт 1607 — транзакцию процесса 344. Запросы одинаковые, различаются только параметры: `$2` в `CONTEXT` — товар, на котором жертва ждала. Поэтому по тексту запроса порядок не виден, его надо смотреть в параметрах и в самих заказах. `CONTEXT` бывает трёх видов: `while updating tuple`, `while rechecking updated tuple` (строку успел изменить другой, и база перепроверяет её), `while locking tuple`. Смысл один: ожидание строки товара.

Строки `LOG: … acquired …` и `still waiting for …` — это ожидания дольше `deadlock_timeout` без дедлока, их пишет `log_lock_waits`. В залпе их больше, чем самих дедлоков: на одну строку товара встаёт очередь, и следующие ждут блокировку самой строки (`ExclusiveLock on tuple`). Если в круге больше двух процессов, `DETAIL` длиннее: на стенде в залпе бывают круги из 2–6 процессов, и запись о дедлоке занимает до 16 строк. Поэтому в команде `-A20`: последняя запись в выводе видна целиком, до `STATEMENT`.

<details>
<summary>Теория PostgreSQL: блокировки строк, дедлоки, диагностика</summary>

### Блокировки строк
- `UPDATE` берёт блокировку на каждую изменяемую строку и держит её до конца транзакции. Другая транзакция, которая хочет изменить ту же строку, ждёт.
- В журнале и в `pg_locks` ожидание строки выглядит как ожидание завершения чужой транзакции: `ShareLock on transaction`.
- Обычное чтение `SELECT` строки не блокирует и не ждёт. Поэтому дедлоки возникают между записывающими транзакциями, а читающие страдают только косвенно, из-за занятого пула.

### Дедлок
- Дедлок — цикл ожиданий. Дождаться разрешения самому нельзя, кто-то должен отступить.
- PostgreSQL не ищет циклы на каждом ожидании: сначала транзакция ждёт `deadlock_timeout`, и только после этого запускается проверка. Если за это время блокировка освободилась, проверка не нужна.
- Когда цикл найден, одна из транзакций откатывается с SQLSTATE `40P01`, остальные продолжают. Её клиент получает ошибку и должен сам решить, повторять ли.
- Откаченная жертва делает свою работу впустую: она ждала, держала соединение, а потом всё откатилось.

### Как база помогает диагностике
- `pg_stat_database.deadlocks` — счётчик дедлоков по базе. Он ведёт учёт даже тогда, когда клиент ошибку не увидел.
- `log_lock_waits` пишет в журнал ожидания блокировок дольше `deadlock_timeout`.
- `log_parameter_max_length_on_error` добавляет в журнал значения параметров запроса: без них видно, что `UPDATE` одинаковые, и не видно, какие товары.
- Во время ожидания текущие блокировки видны в `pg_locks`.

### Порядок блокировок
Общее правило: если всем транзакциям нужны одни и те же блокировки, пусть каждая берёт их в одном и том же порядке (например, по возрастанию `id`). Цикл тогда невозможен: у ожиданий появляется направление. Порядок должен задавать тот, кто берёт блокировки, а не тот, кто эти данные хранит или читает. Поэтому сортировка внутри `placeOrder` надёжнее сортировки в выборке.

</details>

<details>
<summary>Все починки: верные с оговорками и ложные с объяснением</summary>

### Верные починки (все проходят проверку)

| правка | почему работает | оговорки |
|---|---|---|
| Отсортировать копию позиций по `product_id` в начале `placeOrder` | Все транзакции берут товары по возрастанию `id`, цикл невозможен. | Порядок корзины в новом заказе не сохраняется. Нужен для показа — храни исходную позицию отдельно. |
| `SELECT 1 FROM products WHERE id = ANY($1) ORDER BY id FOR UPDATE` в начале транзакции | Строки блокируются сразу и в порядке `id`, а дальнейшие `UPDATE` ждать уже не будут. | Нужен драйверный адаптер массива (`pq.Array`). Явный `ORDER BY id` обязателен. |
| Сортировка в `createOrder` и `ORDER BY product_id` в `orderItems` вместе | Закрыты оба источника порядка. | Порядок держится на двух местах, и третье место, вызывающее `placeOrder`, снова его сломает. Надёжнее одна сортировка в `placeOrder`. |
| Сортировка плюс повтор при `deadlock` | Сортировка убирает причину, повтор остаётся вторым слоем. | Повтор без сортировки ложный: он только прячет дедлоки. |
| Глобальный мьютекс на `placeOrder` | Одновременно идёт один заказ, цикла нет. | Работает в пределах одного процесса: с несколькими репликами сервиса дедлок вернётся. Упирается в пропускную способность: проверка запускает его под распродажей. |
| Пул на одно соединение (`maxOpenConns = 1`) | Все запросы идут по очереди через одно соединение. | Те же ограничения, что у мьютекса, и ещё читающие запросы ждут записывающих. Проверка запускает его под распродажей. |
| `pg_advisory_xact_lock(1)` в начале транзакции | Одна общая блокировка в базе: заказы идут по очереди. Работает и на нескольких репликах. | Вся запись заказов идёт в одну очередь, пропускная способность ограничена одним заказом за раз. |

`UPDATE products ... WHERE id = ANY(...)` одним запросом в список не входит: порядок, в котором PostgreSQL берёт строки, физический и меняется после обновлений. Вердикт для такого решения был бы случайным, поэтому его не проверяют. Не рассчитывай на него как на починку.

### Ложные починки (проверка их ловит)

| попытка | что происходит на самом деле |
|---|---|
| `svc restart` | Порядок блокировок не меняется. На первом же залпе база снова находит дедлоки. |
| Повтор заказа при `deadlock` без сортировки | Клиент ошибки не видит, но цикл остаётся: каждая жертва ждёт `deadlock_timeout`, откатывается и делает всю работу заново. Счётчик `pg_stat_database.deadlocks` растёт. |
| `lock_timeout` 50 мс и повтор | Ожидание обрывается раньше, чем база ищет цикл. Дедлоков в счётчике нет, но транзакции откатываются: растёт счётчик откатов, в номерах заказов появляются дыры (номер берётся из последовательности, она не откатывается). |
| `lock_timeout` и откат до точки сохранения | Счётчик откатов и номера заказов не меняются, но строки товаров обновляются второй раз: их обновлений больше, чем позиций в оформленных заказах. |
| `deadlock_timeout = 10ms` | Циклы от этого не возникают и не исчезают: база находит те же циклы за 10 мс вместо 200, жертва откатывается так же, счётчик дедлоков растёт. В проде к тому же поиск цикла запускается на каждом ожидании дольше 10 мс. |
| `deadlock_timeout = 1h` | Поиск цикла практически отключён: транзакции из цикла висят в базе и держат блокировки и соединения. `TimeoutHandler` через 1 с отвечает клиенту 503, но транзакцию не отменяет: `Begin` вызван без контекста. На стенде через 35 с все 15 соединений пула заняты транзакциями, которые ждут `Lock` 34 с, и `GET /products/1` отвечает 503 за 1,0 с. Дедлоков и откатов нет, есть только неудачные ответы. |
| Пересортировать `position` в базе | Лечит только старые заказы. Новые приходят в `POST /orders` во встречном порядке, и цикл возвращается. |
| Индекс под подсчёт скидки | Транзакция короче, встреч меньше. Порядок блокировок прежний, а залп одновременных заказов цикл всё равно создаёт. |
| `ORDER BY product_id` только в выборке | Повторы из истории выправлены, а заказы из `POST /orders` идут в порядке тела запроса. |
| Сортировка только в `createOrder` | Новые заказы выправлены, а повторы из истории берутся из `orderItems` в порядке `position`. |
| Заглушка вместо повтора: ответ 201 без оформления | Дедлоков нет, но заказ не оформлен: в ответе приходит номер исходного заказа, а не нового. |
| Читать остаток через `SELECT`, писать значением | Сортировка есть, дедлока нет, но две транзакции читают остаток 1 и обе пишут 0. Последний товар продан нескольким покупателям. |
| Убрать транзакцию (`tx := s.db`) | Блокировки не держатся, дедлока нет. Но при отказе по раскупленному товару предыдущие позиции уже списаны и не откатываются. |
| Убрать `AND stock >= $1` | Проверка остатка пропала. Заказ с раскупленным товаром не получает 409, а упирается в ограничение `stock >= 0` в схеме и заканчивается ошибкой. |

`SERIALIZABLE` в проверку не включён. Замер при разработке: дедлоки `40P01` остаются, к ним добавляются ошибки сериализации `40001`. Какая подсказка сработает, зависело бы от того, что случится раньше, поэтому вариант не проверяется.

</details>

<details>
<summary>Как устроена проверка починки</summary>

Проверка смотрит на поведение системы, а не на текст правки. Сбой в залпе зависит от планировщика, а не от сида, поэтому проверка шлёт собственные залпы и судит по признакам в системе.

1. **«Много заказов с общими товарами оформляются разом без сбоев в базе».** 10 раундов по 16 покупателей. В каждом раунде идут повторы двух встречных заказов, которые лежат в образе, и два встречных заказа через `POST /orders` на товарах 701–703: их нагрузка не трогает. Так ловятся оба источника порядка. Счётчики базы читаются до и после, с паузой 11 с (простаивающее соединение PostgreSQL 15+ отправляет накопленную статистику с задержкой до 10 с). Проваливается, если:
   - выросло `deadlocks`: подсказка про дедлоки;
   - один номер заказа выдан дважды: так ловится заглушка, которая отвечает номером из пути;
   - есть неудачные ответы: подсказка про откаты, если выросло число откатов, иначе про зависшие запросы;
   - в номерах оформленных заказов есть дыры, то есть были брошенные попытки;
   - товары обновлялись чаще, чем оформлено позиций: работа делалась дважды;
   - статистика базы сброшена во время проверки.
2. **«Повтор заказа списывает товары и сохраняет состав».** Создаёт заказ, повторяет его: остаток каждого товара уменьшился на количество в заказе, состав нового заказа совпал с исходным (без учёта порядка), номер не совпадает с исходным. Заглушку отверг бы и он, но до него дело не доходит: она падает на первой проверке.
3. **«Заказ с раскупленным товаром не списывает остальные».** Раскупленный товар стоит в корзине последним. Ответ должен быть 409, остатки остальных позиций не изменились. Так ловятся «без транзакции» и «без проверки остатка».
4. **«Последний товар достаётся одному покупателю».** Для шести товаров с остатком 1 по 8 покупателей одновременно: ровно один заказ и остаток 0. Так ловится «читать и писать значением».

Подсказка при провале привязана к признаку в системе, а не к проверке, где случился провал: одна и та же ложная починка не получает разные подсказки в зависимости от того, где именно она споткнулась.

</details>

<details>
<summary>Как не допустить в проде</summary>

- **Правило:** если транзакция берёт несколько блокировок на однотипные строки, порядок берёт тот, кто их берёт, и он один для всех (по возрастанию `id`). Сортируй в одной функции, которую вызывают все. Повтор при `40P01` годится как второй слой поверх верного порядка, не вместо него.
- **Тесты:** интеграционный тест на настоящей базе: залп одновременных заказов с одними товарами во встречном порядке, затем проверка, что `pg_stat_database.deadlocks` не выросло. Без залпа дедлок может не воспроизвестись: в тишине транзакции не пересекаются.
- **Контекст запроса:** `s.db.BeginTx(r.Context(), nil)` и запросы с контекстом. Тогда таймаут ответа отменяет и транзакцию, и зависшая работа не держит соединения пула. Таймаут ответа без отмены работы — та же ловушка, что «таймаут ожидания ≠ отмена» в Go.
- **Метрики и алерты:** алерт на рост `pg_stat_database.deadlocks`; в Prometheus это метрика `pg_stat_database_deadlocks` из `postgres_exporter`. Следи за долей ответов 5xx на ручках записи и за временем ожидания соединения из пула. Включи `log_lock_waits` и `log_parameter_max_length_on_error`: без них журнал не покажет, на каких данных случился цикл.
- **PostgreSQL в облаке и Kubernetes:** в управляемой базе (RDS, Cloud SQL) эти параметры меняются через группу параметров или флаги. Несколько реплик сервиса делают мьютекс в процессе бесполезным: блокировка должна жить в базе. Волны ошибок после пушей и рассылок на нескольких репликах сразу — повод проверить порядок блокировок.
- **Нагрузка:** дедлок зависит не от средней частоты запросов, а от одновременности. Средняя нагрузка может быть невысокой и безопасной, а залп в одну секунду создаёт цикл. Проверяй залпами, а не равномерным потоком.

</details>
