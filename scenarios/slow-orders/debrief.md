# Разбор: «Заказы стали тормозить»

## Что случилось

Список заказов покупателя (`GET /customers/{id}/orders`) ищет заказы по `customer_id`, а индекса по этой колонке в таблице `orders` нет. Без индекса база читает таблицу целиком, строку за строкой, и отбрасывает чужие заказы. Это называется полным проходом (Seq Scan). Пока заказов было мало, проход ничего не стоил. За годы их накопилось около 4 млн (таблица занимает 230 МБ), и каждый такой запрос стал тяжёлым, но шёл редко: примерно один в две секунды, и никто ничего не замечал.

Рассылка подняла частоту этого запроса до 12 в секунду. Каждый проход занимает ядро процессора на сотни миллисекунд, а на стенде их два, и параллельного прохода нет. Двенадцать таких запросов в секунду в два ядра не помещаются, процессор базы забит целиком. Все запросы идут через пул (набор из 15 готовых соединений сервиса с базой), поэтому очередь видна именно там: дешёвые запросы за карточкой товара и на создание заказа ждут свободного соединения за дорогими списками. Когда ожидание доходит до 1 с, `http.TimeoutHandler` обрывает ответ, и клиент получает 503. Вся система тормозит из-за одного запроса.

Быстрая починка: индекс `(customer_id)`. Надёжная: составной индекс `(customer_id, created_at desc)`, собранный через `CONCURRENTLY`, чтобы не заблокировать запись. Он находит заказы одного покупателя сразу и отдаёт их уже по порядку.

## Что сломано в коде

`image/schema.sql`, `service/orders.go` и `service/main.go`:

```sql
CREATE TABLE orders (id bigserial PRIMARY KEY, customer_id int NOT NULL, ...);  -- ① индекс только по id
```

```go
// orders.go, listOrders
rows, err := s.db.QueryContext(r.Context(), `SELECT id, product_id, qty, created_at FROM orders WHERE customer_id = $1 ORDER BY created_at DESC LIMIT $2`, id, pageSize)
//                                                                                    ② фильтр по customer_id       ③ сортировка по дате          ④ 20 строк

// main.go
maxOpenConns = 15                                       // ⑤ все запросы делят 15 соединений
h := http.TimeoutHandler(mux, time.Second, "timeout\n") // ⑥ ответ не позже 1 с
```

По отдельности каждая строка разумна. Запрос верный: ②, ③ и ④ вместе — ровно то, что нужно странице «мои заказы». Пул из 15 соединений соответствует `max_connections = 25` в базе, а ограничение в 1 с защищает клиента от бесконечного ожидания. Поломка возникает из сочетания ① и ②: запросу нужны заказы одного покупателя, а таблица ничего не знает про `customer_id`. С ростом таблицы стоимость запроса растёт вместе с ней, а общий пул из ⑤ выстраивает за одним дорогим запросом очередь из всех остальных.

## Как это находится

Каждый шаг отвечает на один вопрос. В скобках указана ступень подсказок, которая ведёт к тому же шагу.

**1. Сервис падает или тормозит?** (подсказка «Что говорят графики»)
```
svc status
```
Процесс жив, `перезапусков с начала: 0`. Значит, сервис не падает. На графике время ответа выросло и упёрлось примерно в 1 с: это `TimeoutHandler`. Запросы не падают сразу, а долго чего-то ждут.

**2. Какие адреса медленные?** (подсказка «Что в логах»)
```
svc logs
```
Останови вывод через Ctrl+C. Смотри на `dur=`: у `/customers/…/orders` сотни миллисекунд, у `/products/…` ноль-единицы. Значит, один адрес заметно дороже остальных.

**3. Чем занята система?** (подсказка «Чем занят пул»)
```
curl localhost:8080/debug/dbstats
```
Сравни `in_use` с `max_open` и следи за `wait_count`: он растёт волнами. Теперь посмотри, чем заняты сессии в базе:
```
psql -U postgres -d shop -c "select wait_event_type, wait_event, left(query, 80) from pg_stat_activity where datname='shop' and state='active'"
```
Почти все сессии `active` и выполняют один запрос — список заказов с `customer_id = $1`. Колонки `wait_event_type` и `wait_event` пусты: сессия никого не ждёт (не блокировка, не диск), она считает на процессоре. Проверь процессор:
```
top -b -n1 | head -15
nproc
```
`0.0 id` и `nproc` равен 2: ядра заняты целиком. Значит, кончился не пул, а процессор базы, а пул — место, где видна очередь.

**4. Почему запрос дорогой?** (подсказка «Почему запрос дорогой»)
```
psql -U postgres -d shop -c "explain analyze select * from orders where customer_id = 5 order by created_at desc limit 20"
```
В плане ищи `Seq Scan on orders` и строку `Rows Removed by Filter`: прочитано 4 млн строк, а нужно было вернуть 20. Значит, база не умеет найти заказы покупателя иначе, чем перебором.

**5. Чем бы она могла найти их быстрее?** (подсказка «Что есть у таблицы»)
```
psql -U postgres -d shop -c "\d orders"
```
Раздел `Indexes` стоит в середине вывода, после него идут внешние ключи (`Foreign-key constraints`). Индекс там только `orders_pkey` по `id`. Индекса, начинающегося с `customer_id`, нет.

**6. Какой индекс нужен?** (подсказка «Какой индекс нужен») Сверь запрос с таблицей: он фильтрует по равенству (`customer_id = $1`), потом сортирует (`ORDER BY created_at DESC`). Колонка равенства стоит в индексе первой, колонка сортировки второй: тогда база находит покупателя, а заказы внутри него уже лежат по порядку. Точная команда — в ступени «Готовая правка», она описана ниже.

**7. Почему это началось сегодня?** Таблица большая уже давно, а запрос по ней шёл редко: около 0,5 в секунду в спокойное время. Рассылка подняла его до 12 в секунду. Причина в отсутствии индекса, а не в рассылке, она лишь вскрыла проблему.

## Как чинить

Базе нужен способ найти заказы одного покупателя, не читая чужие.

- **Быстро:** индекс по одной колонке, `create index on orders (customer_id)`. База находит все заказы покупателя (у обычного их около 200) и сортирует их сама. Оговорка: без `CONCURRENTLY` сборка блокирует запись в таблицу, а сортировка остаётся, и 200 заказов лежат на 200 разных страницах таблицы, которые надо прочитать.
- **Эталон:** составной индекс `(customer_id, created_at desc)`, собранный `CONCURRENTLY`. Он убирает и полный проход, и сортировку: база читает первые 20 записей индекса и останавливается, то есть 20 страниц таблицы вместо 200. Без `CONCURRENTLY` на время сборки встанут новые заказы. Стенд такую правку примет, а на живой базе с записью так делать нельзя.

```
psql -U postgres -d shop -c "create index concurrently orders_customer_created on orders (customer_id, created_at desc)"
```

Дождись ответа `CREATE INDEX`: под нагрузкой сборка занимает десятки секунд. `svc deploy` не нужен, новый план подхватится сразу. Если ответ `already exists`, посмотри `\d orders`. Если у индекса пометка `INVALID`, прошлая сборка прервалась: удали его (`drop index concurrently orders_customer_created`) и повтори. Если пометки нет, индекс уже готов.

## Почему очевидные «починки» не работают

Проверка смотрит на поведение системы, а не на текст правки: она грузит сервис трафиком выше рассылки, сверяет списки заказов с ожидаемыми и сравнивает задержки.

- **Рестарт сервиса или базы, `vacuum analyze`:** план запроса не меняется, и каждый запрос по-прежнему читает 4 млн строк. Статистика и так свежая.
- **Больше пул и соединений:** соединений хватает, `wait_count` перестаёт расти, пул выглядит здоровым. Но десятки проходов делят те же два ядра, каждый длится дольше 1 с и отменяется. Пул здоров, процессор базы забит.
- **Память и параллельные воркеры:** `shared_buffers` ничего не даёт, таблица и так лежит в кеше операционной системы. Параллельный проход ускоряет один запрос не больше чем вдвое, но под нагрузкой процессор уже занят, пропускной способности это не добавляет.
- **Индекс по дате без `customer_id`:** база идёт по индексу от новых заказов к старым и ищет нужного покупателя. У обычного покупателя заказы лежат через каждые 20 000 записей, и проход укладывается в десятки миллисекунд, а у редкого с тремя старыми заказами проходит почти весь индекс, около секунды.
- **Заглушка, `statement_timeout`, фильтр «за 90 дней», удаление старых заказов:** ответ быстрый, но неполный или пустой. Проверка сверяет списки прямо под нагрузкой, а глубину истории проверяет отдельно.
- **Кеш в памяти:** он не помогает тем, кого в нём ещё нет. Проверка читает тысячи разных покупателей, и первый запрос каждого стоит столько же, а после перезапуска кеш пуст.

## Правило на будущее

> Тормозят все адреса → какой запрос выполняет база и на чём она ждёт (пусто = считает на процессоре) → как она его выполняет (план) → есть ли индекс, начинающийся с колонки фильтра.
> Пул показывает очередь, но не причину; индекс собирают в порядке «сначала равенство, потом сортировка», а быстрый неполный ответ хуже медленного верного.

<details>
<summary>Механика по звеньям: от строки запроса до 503</summary>

1. Запрос списка приходит в `listOrders`, и сервис берёт из пула соединение.
2. База не находит индекса по `customer_id` и читает таблицу `orders` целиком (230 МБ, она лежит в кеше операционной системы, диск не нужен), отбрасывая чужие заказы. Из подходящих строк она оставляет 20 самых новых.
3. Проход выполняется на процессоре. Ядер два, параллельного прохода нет, поэтому при 12 запросах в секунду проходы делят ядра и каждый идёт дольше, чем в одиночку. Ожидания блокировок или диска у сессий нет.
4. Соединение занято всё время прохода, и пул лишь отражает это: `in_use` в моменте от 5 до 14 из 15, `wait_count` растёт волнами. Любой другой запрос, даже простой `SELECT … FROM products WHERE id = $1`, ждёт свободного соединения за дорогими.
5. Через 1 с контекст запроса истекает, `TimeoutHandler` отдаёт клиенту 503. Драйвер `lib/pq` шлёт базе запрос на отмену и закрывает соединение, пул открывает новое. Работа не копится, но всё, что отменённый запрос успел сделать, потрачено зря. В журнале базы это строки `canceling statement due to user request`.
6. Новые запросы продолжают приходить, поэтому очередь не рассасывается, пока нагрузка выше пропускной способности процессора.

</details>

                 |            | select wait_event_type, wait_event, left(query, 80) from pg_stat_activity where

`wait_event_type` пуст у всех: сессия ничего не ждёт, а считает. Если бы там стояло `Lock`, причина была бы в блокировке, `IO` — в диске, `Client` — в простое. Сессии в `idle in transaction` означали бы открытую транзакцию, а не дорогой запрос.

Индекс только на `id`. Внешний ключ — не индекс по `product_id`.

Indexes:
    "orders_pkey" PRIMARY KEY, btree (id)
    "orders_customer_created" btree (customer_id, created_at DESC)

Вместо `Seq Scan` — `Index Scan using orders_customer_created` с условием `Index Cond` и без отдельного `Sort`. Для 15000 — 0,149 мс, для 30001 — 0,043 мс. После правки `curl localhost:8080/debug/dbstats` показывает `"in_use":0`.

**После индекса по дате** (`create index on orders (created_at)`).

Обычным покупателям хватает десятков миллисекунд: 20 нужных заказов набираются через 300–400 тыс. отброшенных записей. У покупателя с тремя старыми заказами `Rows Removed by Filter` почти равен размеру таблицы, около секунды.

**После индекса в обратном порядке** (`create index on orders (created_at, customer_id)`).
```

customer_id = 15000: Index Scan Backward using orders_date_cust ... Index Cond: (customer_id = 15000)   Execution Time: 13.588 ms
```
Условие по `customer_id` проверяется внутри индекса (`Index Cond`), без обращения к таблице. Но диапазон поиска не сужается: индекс всё равно обходится по датам, пока не наберётся 20 записей.

**Сортировка по `id` вместо даты.**

   Rows Removed by Filter: 4000950

```
Список по содержанию верный (id и дата растут вместе), но обратный проход по ключу у редкого покупателя занимает почти 3 с.

customer_id = 30001 limit 20:  1, 2, 3
```
База отдаёт строки в физическом порядке, то есть по возрастанию `id`: 20 самых старых заказов, а не 20 самых новых. У обычного покупателя 15000 это август-сентябрь 2026 вместо октября, у редкого `1, 2, 3` вместо `3, 2, 1`.

**Фильтр «за 90 дней».**
```
select count(*) from (select id from orders where customer_id = 15000 and created_at > now() - interval '90 days' order by created_at desc limit 20) s
 count: 10

select max(created_at), now() from orders where customer_id > 100
 2026-10-21 05:40:00+00 | 2026-11-09 21:59:18+00
```
Из 20 заказов остаётся 10: история обычных покупателей кончается 2026-10-21. Результат зависит от календаря.

**После прерванной сборки.**
```
Indexes:
    "orders_pkey" PRIMARY KEY, btree (id)
    "orders_customer_created" btree (customer_id, created_at DESC) INVALID
```
Индекс есть в списке, но с пометкой `INVALID`, и планировщик его не использует. `drop index concurrently orders_customer_created` его убирает, после этого сборку можно повторить.

</details>

<details>
<summary>Теория PostgreSQL: полный проход, индекс, порядок колонок, CONCURRENTLY</summary>

### Полный проход и индекс
- Без индекса база читает таблицу страница за страницей и проверяет условие в каждой строке (`Seq Scan`). Стоимость растёт вместе с размером таблицы, а не с числом нужных строк.
- Индекс — отдельная структура (B-дерево), в которой значения отсортированы. По нему база находит нужные записи за несколько чтений страниц.
- `Rows Removed by Filter` в плане — строки, которые прочитаны и отброшены. Если это число на порядки больше `rows` у верхнего узла, запросу не хватает индекса.
- `wait_event` в `pg_stat_activity` говорит, чего ждёт сессия. Пустое значение у `active` — сессия работает на процессоре; `IO` — ждёт диск; `Lock` — блокировку.

### Порядок колонок в составном индексе
- Запись в индексе `(customer_id, created_at desc)` отсортирована сначала по покупателю, внутри него по дате. Поэтому все заказы одного покупателя стоят рядом и уже по порядку, и `LIMIT 20` останавливает чтение после 20 записей.
- Индекс только по `created_at` отсортирован по дате для всей таблицы. Он помогает порядку, но не поиску покупателя: база идёт по нему и проверяет каждую строку.
- Индекс `(created_at, customer_id)` проверяет покупателя уже внутри индекса, без похода в таблицу, но первая колонка не сужает диапазон: обход по датам идёт, пока не наберётся 20 подходящих записей. В PostgreSQL 18 появился skip scan (пропуск значений первой колонки), но здесь первая колонка почти уникальна, и он не помог бы.
- Колонку равенства ставят первой, колонку сортировки второй. Наоборот не работает.

### Индекс только по `customer_id`
Он тоже убирает полный проход. У обычного покупателя около 200 заказов, они лежат на 200 разных страницах таблицы: база прочитает их все и отсортирует. Составной индекс даёт нужные 20 записей сразу в порядке, то есть читает 20 страниц.

### BRIN
BRIN хранит для каждого диапазона блоков (по умолчанию 128 страниц, здесь около 17 тысяч строк) только минимум и максимум. Он хорош, когда значения расположены на диске по порядку. Покупатели обычного диапазона идут циклом (номер покупателя растёт и возвращается), поэтому каждый диапазон охватывает почти весь цикл и отсекается мало. Для редких покупателей, которые лежат в первых страницах, BRIN полезен, а поток обычных остаётся тяжёлым.

### `CREATE INDEX CONCURRENTLY`
- Обычный `CREATE INDEX` на время сборки блокирует запись в таблицу. Чтения идут, а новые заказы встают.
- `CONCURRENTLY` собирает индекс за два прохода и не блокирует запись, но идёт дольше и не работает внутри транзакции (многие инструменты миграций по умолчанию оборачивают каждую миграцию в транзакцию).
- Если сборка прервалась (таймаут, отмена), остаётся индекс со статусом `INVALID`. Планировщик его игнорирует, но запись продолжает обновлять. Его нужно удалить и собрать заново.
- Удалять нужно тоже через `drop index concurrently`: обычный `DROP INDEX` берёт самую строгую блокировку таблицы и под нагрузкой встаёт в очередь, блокируя чтение и запись.

### Пул соединений и отмена
- Пул ограничивает число одновременных запросов к базе. Когда он занят, новые запросы ждут соединения, и это ожидание входит в задержку любого адреса. Поэтому один дорогой запрос портит ответы всем остальным.
- Пул не создаёт нагрузку, он показывает её. Если соединения заняты сессиями, которые считают на процессоре, увеличение пула добавляет конкурентов за те же ядра.
- Когда контекст запроса истекает, драйвер шлёт базе запрос на отмену и закрывает соединение. Сам запрос в базе прерывается, но потраченное время уже не вернуть.

<summary>Все починки: верные с оговорками и ложные с объяснением</summary>

### Верные починки (все проходят проверку)

| правка | почему работает | оговорки |
|---|---|---|
| `create index concurrently orders_customer_created on orders (customer_id, created_at desc)` | Находит заказы покупателя сразу и отдаёт в нужном порядке, без сортировки. | Эталон. Собирай через `CONCURRENTLY`. |
| `create index on orders (customer_id)` | Убирает полный проход, база сортирует только заказы одного покупателя. | Сортировка остаётся, читаются 200 страниц вместо 20. Без `CONCURRENTLY` блокирует запись на время сборки. |
| Сначала `create index on orders (created_at)`, потом `create index on orders (customer_id)` | Верный индекс добавлен, планировщик выбирает его. | Лишний индекс по дате замедляет вставки и занимает место, его стоит удалить. |

### Ложные починки (проверка их ловит)

| попытка | что происходит на самом деле |
|---|---|
| `svc restart` | План запроса не меняется, каждый запрос по-прежнему читает всю таблицу. |
| Перезапуск базы | То же: после запуска план прежний. |
| Пул 150 и `max_connections = 200` | Соединений хватает, `wait_count` перестаёт расти, пул выглядит здоровым. Но 16–30 проходов делят те же два ядра, каждый длится дольше 1 с и отменяется. Пул здоров, процессор базы забит. |
| `shared_buffers = 256MB` и параллельные воркеры | `shared_buffers` ничего не даёт: таблица уже в кеше операционной системы. Параллельный проход ускоряет один запрос не больше чем вдвое, но процессор под нагрузкой уже занят, пропускной способности это не добавляет. |
| `vacuum analyze orders` | Статистика уже свежая, план не меняется. |
| `create index … using brin (customer_id)` | Покупатели идут по таблице циклом, диапазон блоков охватывает почти все значения, и обычным покупателям индекс почти ничего не отсекает. Редким он помогает, провал даёт поток обычных. |
| `statement_timeout = '40ms'` и пустой список вместо ошибки | Дорогой запрос обрывается, клиенту возвращается пустой список с кодом 200. Быстро, но неверно: сверка списков под нагрузкой не пропускает. |
| Кеш в памяти со сбросом при новом заказе | Корректен, но первый запрос каждого покупателя стоит как раньше. Проверка читает тысячи разных покупателей, так что кеш почти не греется, а после перезапуска пуст. |
| Индекс по `created_at` | Для обычного покупателя подходящая запись стоит через каждые 20 000, и 20 заказов набираются за 300–400 тыс. записей (десятки миллисекунд на стенде). Для редкого с тремя старыми заказами приходится пройти весь индекс, около секунды. |
| Индекс `(created_at, customer_id)` | Условие по покупателю проверяется внутри индекса, но диапазон не сужается. На стенде 13,6 мс для обычного и 337 мс для редкого. |
| Сортировка `ORDER BY id DESC` вместо даты | Список верный, но идёт обратный проход по первичному ключу: у редкого покупателя почти 3 с. Ловится скоростью. |
| Фильтр «за последние 90 дней» плюс верный индекс | Запрос быстрый, но у всех обычных покупателей (кроме 1–100, которым нагрузка создаёт свежие заказы) список неполный: история кончается в октябре, и остаётся около 10 из 20. У редких список пуст. Результат зависит от календаря. |
| Удаление заказов старше 2026-01-01 плюс индекс | Редкие покупатели теряют все заказы и получают пустой список. Это видно сверкой списков. |
| Удаление старых заказов обычных покупателей (до 2026-05-01) плюс индекс | Страница из 20 свежих заказов цела, а история глубже потеряна. Видно только по выборке старых заказов через `/orders/{id}`. |
| Заглушка, отвечающая только тем, кого проверяют | Проверка обходит много покупателей из разных диапазонов, а не нескольких известных. |
| Сборка индекса, оборванная таймаутом | Остаётся `INVALID`-индекс, планировщик его не использует, запрос остаётся медленным. |
| Индекс по `customer_id` и запрос без `ORDER BY` | База отдаёт строки в физическом порядке, по возрастанию `id`: 20 самых старых заказов вместо 20 самых новых, у редкого `1, 2, 3`. Не тот набор, а не только порядок. |
| Список заказов всегда пустой | Быстро, но функции нет. Проверка сверяет списки. |

<details>
<summary>Как устроена проверка починки</summary>

Проверка смотрит на поведение системы, а не на текст правки. Пороги: ошибок не больше 0,5%.

1. **«Сервис держит трафик рассылки с запасом».** 25 с нагрузки 45 запр/с, больше рассылки (около 16 списков в секунду против 12). Три четверти списков читают покупатели, которых обычная нагрузка не прогрела (4001–12000), четверть — тех, кто сам делает заказы (1–100), поэтому кеш со сбросом при заказе не спасает. p95 не выше 400 мс. Всё это время каждые 0,2 с сверяется список очередного покупателя, обычного и редкого поочерёдно. При плохом индексе сверки редких покупателей сами нагружают процессор, поэтому индекс по дате иногда падает уже здесь.
2. **«Быстро открываются и заказы редких покупателей».** 10 с нагрузки 35 запр/с только по 200 редким покупателям, p95 не выше 500 мс. Индекс не под этот запрос выдаёт себя потоком: у индекса по дате редкий покупатель стоит около секунды, у `(created_at, customer_id)` — около 340 мс.
3. **«Списки заказов полны и упорядочены».** Списки пяти обычных покупателей, трёх редких и покупателя без заказов сравниваются с ожидаемыми от нового к старому.
4. **«Старые заказы на месте».** Выборка заказов по всей истории через `/orders/{id}`, примерно 200 запросов. Страница списка потерю глубокой истории не показывает, эта проверка показывает.
5. **«Новый заказ сразу виден покупателю».** Создаётся заказ и тут же читается список: новый заказ должен быть первым.
6. **«Сервис держит нагрузку сразу после перезапуска».** Сервис перезапускается, и 8 с идёт та же нагрузка, что в первой проверке, со сверкой списков. Так ловится то, что живёт только в памяти сервиса.

</details>

<details>
<summary>Как не допустить в проде</summary>

- **Правило:** у каждого запроса, который попадает в частый путь, фильтр и сортировка должны ложиться на индекс. Проверяй план (`EXPLAIN`) на данных размером с боевые, а не на пустой базе.
- **Тесты:** нагрузочный прогон на копии боевых объёмов до выката, а не после рассылки.
- **Метрики:** расширение `pg_stat_statements` показывает самые дорогие запросы по суммарному времени. `pg_stat_user_tables.seq_tup_read` вместе с `idx_scan` показывает таблицы, которые читаются полным проходом. `auto_explain` пишет планы медленных запросов в журнал. В сервисе следи за `WaitCount` и `WaitDuration` из `db.Stats()`, а в базе — за `wait_event` в `pg_stat_activity`.
- **Облако:** в управляемой PostgreSQL есть встроенные разборы запросов, например CloudWatch Database Insights (бывший Performance Insights) в AWS или Query Insights в Cloud SQL, они показывают топ запросов по времени и ожиданиям.
- **Kubernetes:** проверки готовности и живости, которые ходят в ручку через общий пул, начинают падать под такой нагрузкой, и кластер сам делает ложную починку «рестарт»: поды перезапускаются, а причина остаётся. Автомасштабирование добавляет поды, и каждый приносит свои 15 соединений: так получается ложная починка «большой пул», только с упором в процессор базы.
- **Страховка поверх индекса:** семафор на число одновременных дорогих списков в сервисе и более длинный таймаут сглаживают симптом, но каждый список остаётся полным проходом. Это защита на случай следующего пропущенного индекса, а не замена ему.
- **Индекс на живой базе:** собирай и удаляй через `CONCURRENTLY`, проверяй после сборки, что индекс не `INVALID`, и убедись, что инструмент миграций не оборачивает команду в транзакцию.

</details>
