# Разбор: «Сайт магазина висит»

## Что случилось

Чтобы оформить заказ, `createOrder` открывает транзакцию, блокирует строку товара (`SELECT … FOR UPDATE`) и смотрит остаток. Пока транзакция открыта, она держит соединение из пула — набора соединений с базой, которые сервис открывает по мере нужды и переиспользует; максимум их 15. Если товара не хватает, обработчик отвечает 409 и выходит, но транзакцию не завершает: ни `Commit`, ни `Rollback`. Соединение остаётся занятым, строка товара остаётся заблокированной, и вернуть их некому.

Следующий заказ на тот же товар встаёт в очередь за блокировкой и держит ещё одно соединение. Клиент через секунду получает 503 от `http.TimeoutHandler` (обёртки, которая обрывает ответ через 1 с), но работа обработчика на этом не останавливается. Отказные заказы (на раскупленный товар или больше остатка) составляют около 2% запросов, и каждый навсегда забирает слот. Когда набирается 15 слотов, пул пуст, и ждут все запросы, в том числе чтение товара: оно с блокировками не конфликтует, но тоже не может получить соединение. Для клиента сайт висит.

Быстрая починка — откат транзакции перед ответом 409. Надёжная — `defer tx.Rollback()` сразу после `Begin`: тогда ни один выход из функции не оставит транзакцию открытой.

## Что сломано в коде

`orders.go`, функция `createOrder`:

```go
tx, err := s.db.Begin()                                    // ① соединение занято до конца транзакции
...
err = tx.QueryRow(`SELECT stock FROM products WHERE id = $1 FOR UPDATE`, req.ProductID).Scan(&stock) // ② строка заблокирована до конца транзакции
if errors.Is(err, sql.ErrNoRows) {
    tx.Rollback()                                          // ③ эти выходы транзакцию закрывают
    writeError(w, http.StatusNotFound, "no such product")
    return
}
...
if stock < req.Qty {
    writeError(w, http.StatusConflict, "sold out")         // ④ выход без Rollback и без Commit
    return
}
```

По отдельности всё разумно. `FOR UPDATE` нужен, чтобы два покупателя не списали последнюю единицу. Ответ 409 для раскупленного товара — правильный. Откат в остальных ветках есть, поэтому код выглядит аккуратно. Для утечки хватает ① и ④: транзакция открыта, а один из выходов про неё забыл. Блокировка ② утечку усиливает: заказ на тот же товар не просто возьмёт новое соединение, он встанет в очередь за утёкшей транзакцией и не выйдет из неё никогда.

## Как это находится

Каждый шаг отвечает на один вопрос. В скобках указана ступень подсказок, которая ведёт к тому же шагу.

**1. Запросы падают сразу или чего-то ждут?** (подсказка «Что говорят графики») Ошибки и время ответа выросли вместе, а время ответа упёрлось примерно в 1 секунду. Это предел `TimeoutHandler`. Значит, запрос не падает сразу, а ждёт, пока его оборвут.

**2. Страдают только заказы или всё?** (подсказка «Что в логах»)
```
svc logs
```
Останови вывод через Ctrl+C. Красные строки `status=503` с `dur` около секунды стоят не только у `POST /orders`, но и у `GET /products/…`, а рядом жирная строка `getProduct: context deadline exceeded`: чтение не дождалось ответа. Жёлтых `status=409` в этой части журнала почти нет: они были только в первую минуту. Если не работает даже чтение, общий ресурс кончился у всех сразу.

**3. Какой ресурс кончился?** (подсказка «Чего ждут запросы»)
```
curl localhost:8080/debug/dbstats
```
Сравни `in_use` с `max_open`: если они равны, все соединения пула заняты. Растущие между замерами `wait_count` и `wait_ms` показывают, что остальные запросы стоят в очереди за соединением.

**4. Кто их занял?** (подсказка «Кто занял соединения»)
```
psql -U postgres -d shop -c "select state, count(*) from pg_stat_activity where datname='shop' group by 1"
```
Ищи состояние `idle in transaction`: транзакция открыта, но ничего не делает. Вместе с сессиями `active`, которые стоят в ожидании блокировки, они составляют все занятые соединения, а запросов, которые что-то делают, нет. Значит, соединения держит не нагрузка, а брошенные транзакции.

**5. Что они делали последним?** (подсказка «Что делают эти сессии»)
```
psql -U postgres -d shop -c "select query from pg_stat_activity where state='idle in transaction'"
```
Последний запрос у всех `SELECT stock … FOR UPDATE`. Такой запрос есть только в одном месте кода.

**6. Какая функция?** (подсказка «Какая функция») Открой `orders.go`: этот запрос выполняет `createOrder`. Пройди все выходы после `Begin` и проверь, завершается ли в каждом транзакция.

**7. Какая ветка?** (подсказка «Какая ветка») Ветка `stock < req.Qty` отвечает 409 и выходит без отката. Любая попытка купить закончившийся товар оставляет транзакцию открытой.

**8. Почему это началось сегодня?** Код был таким всегда. Ветка срабатывает только на заказ, который не хватает товара, а такие заказы редки: на стенде около 2% запросов. Каждый теряет один слот, и пока слотов больше, чем потерь, симптомов нет, хотя утечка идёт с первых секунд: на стенде через 25 секунд уже 7 сессий `idle in transaction`, а `wait_count` равен нулю. Когда накопилось 15, пул пуст. Это занимает от минуты до полутора и зависит от того, на какие товары пришлись отказы; в проде срок зависит от доли отказов и размера пула.

## Как чинить

Каждая транзакция должна завершаться на любом выходе из функции.

- **Быстро:** `tx.Rollback()` перед `writeError(…, 409, "sold out")`. Транзакция закрыта, соединение вернулось в пул, блокировка снята. Оговорка: следующий выход, который добавят позже, снова можно забыть.
- **Эталон:** `defer tx.Rollback()` сразу после проверки ошибки `Begin`. Откат срабатывает при любом выходе, а после успешного `Commit` он ничего не делает, потому что транзакция уже завершена. Забыть выход становится невозможно.

```go
// orders.go, createOrder
tx, err := s.db.Begin()
if err != nil {
    ...
}
defer tx.Rollback()

var stock int
err = tx.QueryRow(`SELECT stock FROM products WHERE id = $1 FOR UPDATE`, req.ProductID).Scan(&stock)
```

Потом сохрани файл, выполни `svc deploy` и нажми «Проверить починку». Остальные откаты в других ветках можно оставить: повторный `Rollback` после завершённой транзакции безвреден.

## Почему очевидные «починки» не работают

Проверка смотрит на поведение системы, а не на текст правки: подаёт шестикратную нагрузку, считает зависшие транзакции и обрывы сессий, разыгрывает гонку за последний товар.

- **Перезапуск сервиса:** при рестарте соединения закрываются, база откатывает транзакции, пул свободен. Но код прежний, и при шестикратной нагрузке отказы на раскупленные товары снова забирают слоты, на этот раз быстрее. Время ответа выходит за 500 мс.
- **Больший пул (150 соединений и `max_connections = 200` в базе):** слотов хватает дольше, но каждая утёкшая транзакция остаётся. Заказы на уже заблокированный товар ждут блокировку и через секунду получают 503 вместо 409. Утечка отодвинута, а не устранена, и в проде она съедает соединения базы, общие для всех сервисов.
- **`idle_in_transaction_session_timeout` в базе:** база сама обрывает брошенные сессии, соединения освобождаются, ошибок почти нет. Но освобождается только сессия в базе. В сервисе каждое такое соединение остаётся занятым навсегда: объект транзакции не узнаёт об обрыве, а `Commit` и `Rollback` никто не вызовет. Ошибок нет лишь потому, что предел пула снят, и `in_use` в `/debug/dbstats` растёт без конца. Обрывы считает счётчик сессий базы, и проверка видит его рост. Утечку спрятали, а не убрали.
- **Проверка остатка до транзакции:** если читать остаток отдельным запросом и отвечать 409 заранее, обычные отказы больше не попадают в ветку с утечкой. Но несколько покупателей одновременно читают «остался 1», и все идут в транзакцию. Первый получает блокировку, покупает, остальные видят 0 и попадают в ветку с утечкой. Первый проигравший отвечает 409 и оставляет строку заблокированной, остальные ждут её вечно и через секунду получают 503. Гонка за последний товар вскрывает это.
- **Условие по `id`:** отвечать 409 для товаров от 198 и выше до `Begin` прячет утечку для известных раскупленных товаров, но отказ бывает и на любом другом, если просят больше, чем есть. Нагрузка проверки как раз такие запросы шлёт на товары 101–197. Такая правка режет и товары 201–600, поэтому ловится по-разному, в зависимости от того, какие товары выпали в отказы: то пул кончается посреди нагрузки, то проваливается гонка за последний товар.
- **Заглушка:** `POST /orders` отвечает 201 и ничего не делает. Остаток товара не меняется, проверка заказов это видит.

## Правило на будущее

> Сайт висит и падает даже чтение → чего ждут запросы (пул) → кто держит соединения (`idle in transaction`) → какой последний запрос → какой выход из функции не завершил транзакцию.
> «Ответили клиенту» ≠ «закончили транзакцию»: ответ и завершение транзакции — два разных действия, и второе нужно на каждом выходе.

<details>
<summary>Механика по звеньям: от строки кода до ошибки клиента</summary>

1. Приходит заказ на раскупленный товар, например 199. `Begin` берёт соединение из пула (①), `SELECT … FOR UPDATE` блокирует строку товара (②).
2. Остаток 0 меньше количества, ветка отвечает 409 и выходит (④). Ни `Commit`, ни `Rollback` не вызваны. Клиент получил ответ и доволен, а транзакция осталась открытой.
3. Для базы это сессия в состоянии `idle in transaction`: она ничего не выполняет, но держит блокировку строки. Для Go это объект `Tx`, который держит соединение: оно вернётся в пул только после `Commit` или `Rollback`.
4. Второй заказ на товар 199 доходит до `SELECT … FOR UPDATE` и ждёт блокировку, которую никто не снимет. Он занимает второе соединение. `TimeoutHandler` через секунду отвечает клиенту 503, но обработчик не останавливается: `Begin` вызван без контекста, и отмена до базы не доходит.
5. Так же копятся отказы на других раскупленных товарах и на обычных, если просят больше, чем есть. Каждый товар даёт один «держатель» блокировки и очередь за ним.
6. Пул заполняется. Новый запрос на любую ручку ждёт соединение из пула. `GET /products/…` с утёкшими блокировками не конфликтует: обычный `SELECT` не ждёт чужих блокировок строк. Но соединения нет, и через секунду он тоже получает 503 (в журнале `getProduct: context deadline exceeded`).
7. Сервис остаётся живым: `svc status` показывает запущен, перезапусков нет. Висит он потому, что ему нечем говорить с базой.

</details>

<details>
<summary>Теория Go и PostgreSQL: пул соединений, транзакции, блокировки</summary>

### `database/sql`
- `sql.DB` — это пул соединений. `SetMaxOpenConns(n)` ограничивает число одновременно открытых; когда все заняты, следующий вызов ждёт освобождения.
- `db.Begin()` берёт соединение из пула и закрепляет его за транзакцией. Вернётся оно только после `Commit` или `Rollback`.
- Если в обработчике забыть завершить транзакцию, соединение не вернётся в пул, пока жив процесс. Сборщик мусора тут не помогает: объект `Tx` ждёт завершения сам.
- `db.Stats()` показывает `InUse`, `Idle`, `WaitCount`, `WaitDuration`. Сервис отдаёт их через `/debug/dbstats`. Если `InUse` стоит на максимуме при ровной нагрузке, соединения кто-то держит.
- `BeginTx(ctx, nil)` привязывает транзакцию к контексту: при отмене контекста пакет откатывает её сам. `Begin()` контекста не знает.

### `http.TimeoutHandler`
Через заданное время он отвечает клиенту 503 и отменяет контекст запроса, но не останавливает сам обработчик. Если обработчик ждёт в коде, который контекст не слушает (как `Begin()` и `tx.QueryRow` без контекста), он продолжит стоять и держать соединение. Ответ клиенту и освобождение ресурсов — разные вещи.

### PostgreSQL
- Сессия в состоянии `idle in transaction` — транзакция открыта, запросов сейчас нет. Она держит все свои блокировки до конца. Опасна именно долгая такая сессия.
- `SELECT … FOR UPDATE` блокирует строки так же, как `UPDATE`. Обычный `SELECT` строки не блокирует и не ждёт, поэтому чтение товара не конфликтует с утёкшей транзакцией: оно страдает только из-за пустого пула.
- Сессия, которая ждёт чужую блокировку, находится в состоянии `active` и в `wait_event_type` показывает `Lock`.
- `max_connections` — общий предел соединений к базе от всех клиентов. Пул, который выдаёт больше, чем у базы свободно, отнимает их у остальных сервисов.
- `idle_in_transaction_session_timeout` — настройка, по которой база сама обрывает сессии, простоявшие в транзакции дольше срока. Такие обрывы считаются в `pg_stat_database.sessions_fatal`. Это страховка на случай утечки, а не её исправление: в приложении транзакция остаётся незавершённой, и слот в пуле не освободится до перезапуска процесса.

</details>

<details>
<summary>Все починки: верные с оговорками и ложные с объяснением</summary>

### Верные починки (все проходят проверку)

| правка | почему работает | оговорки |
|---|---|---|
| `tx.Rollback()` перед ответом 409 | Транзакция закрывается, соединение возвращается в пул, блокировка снимается. | Следующий добавленный выход можно снова забыть. |
| `defer tx.Rollback()` сразу после `Begin` | Откат срабатывает на любом выходе. После успешного `Commit` он ничего не делает. | Эталон. Старые явные `tx.Rollback()` в других ветках можно не убирать. |

`BeginTx(r.Context(), nil)` вместо `Begin()` по коду тоже закрывает утечку: `TimeoutHandler` отменяет контекст, когда обработчик вернул управление, `database/sql` откатывает транзакцию, а драйвер `lib/pq` закрывает соединение. Цена — переподключение на каждый отказ. На стенде этот вариант не проверялся, в `repairs.go` его нет.

### Ложные починки (проверка их ловит)

| попытка | что происходит на самом деле |
|---|---|
| `svc restart` | Соединения закрываются, транзакции откатываются, пул свободен. Код тот же, поэтому при шестикратной нагрузке отказы снова забирают слоты, и время ответа превышает 500 мс. |
| Заглушка: `POST /orders` отвечает 201 с номером 1 | Ничего не оформляется, остаток товара не меняется. Ловит проверка заказов. |
| Больший пул: `maxOpenConns = 150` и `max_connections = 200` с перезапуском базы | Слотов хватает дольше, но утёкшие транзакции остаются. Заказы на заблокированный товар ждут блокировку и через 1 с получают 503 вместо 409. Доля таких ошибок на нагрузке держится около порога 0,5% (от 0,5 до 1,2% в зависимости от случая): порог здесь не свойство поломки, а граница сравнения. Если нагрузка всё же прошла, проверка заказов всё равно получит 503 на раскупленном товаре 199: первый заказ утечёт, второй встанет за его блокировкой. В проде такой пул ещё и отнимает соединения у других сервисов. |
| Убрать проверку остатка (`_ = stock`) | Ветка с утечкой исчезла, но и защиты от продажи сверх остатка нет. `UPDATE` упирается в ограничение `stock >= 0` схемы, ветка откатывает транзакцию и отвечает 500 вместо 409 (в журнале `createOrder: update: … violates check constraint …`). Ошибок около 2%, зависших транзакций нет, поэтому проверка проваливается на нагрузке без подсказки про утечку. |
| Отсечка по `id`: для товаров от 198 отвечать 409 до `Begin` | Утечка в коде осталась, спрятана от известных раскупленных товаров. Нагрузка проверки шлёт заказы с количеством 1 000 000 на товары 101–197, и они попадают в ту же ветку. Правка заодно отвечает 409 на товары 201–600, у которых остаток 1. В зависимости от случая её ловит либо нагрузка (пул кончается посреди проверки, p95 около секунды), либо гонка за последний товар (заказов 0, остаток 1). Подсказка зависит от того, какая проверка провалится первой. |
| Проверка остатка отдельным запросом до транзакции | Обычные отказы не доходят до ветки с утечкой. Но в гонке за последнюю единицу несколько покупателей одновременно читают «остался 1». Первый получает блокировку и покупает, следующий видит 0, отвечает 409 и оставляет строку заблокированной, остальные шесть ждут её вечно и через 1 с получают 503. Пул при этом не пуст (занято около 7 слотов из 15): 503 даёт ожидание блокировки. |
| `idle_in_transaction_session_timeout = '10ms'` и пул без предела | База рвёт брошенные сессии вместе с их блокировками, но каждое соединение в сервисе остаётся занятым навсегда: транзакция не завершена, объект `Tx` об обрыве не знает. С пределом пула сервис всё равно встал бы, поэтому предел снят, и `in_use` растёт без конца. Ошибок нет только из-за этого. Счётчик оборванных сессий в базе растёт, проверка сверяет его до и после нагрузки. |

</details>

<details>
<summary>Как устроена проверка починки</summary>

Проверка смотрит на поведение системы, а не на текст правки. Пять проверок идут по порядку и останавливаются на первом провале.

1. **«Сервис держит шестикратную нагрузку».** 30 секунд по 60 запросов в секунду, смесь та же, что на стенде. Перед нагрузкой и после читается счётчик сессий, которые база оборвала (`sessions_fatal + sessions_killed`). Проваливается, если:
   - p95 выше 500 мс: подсказка про перезапуск;
   - доля ошибок выше 0,5%: если после нагрузки в базе остались зависшие транзакции, подсказка про больший пул;
   - счётчик оборванных сессий вырос: подсказка про таймаут в базе, утечка спрятана.

   Внутри нагрузки порядок именно такой: p95, затем доля ошибок, затем обрывы сессий.
2. **«Заказы списывают остаток, а проданный товар не продаётся».** Пять заказов на товар 7: остаток должен уменьшиться ровно на пять. Затем 20 заказов на раскупленный товар 199: все должны вернуть 409, остаток остаться нулевым. Ответ 503 здесь даёт подсказку про больший пул. Заглушку ловит первая часть, без подсказки: остаток после пяти заказов не изменился. Если нагрузка прошла при большом пуле, здесь ловится и он: первый заказ на 199 утекает, второй ждёт его блокировку и получает 503.
3. **«Последний товар достаётся одному покупателю».** Шесть товаров с остатком 1, на каждый по восемь покупателей одновременно: ровно один ответ `201 Created`, остальные 409, остаток 0. Ответ 503 даёт подсказку про проверку остатка до транзакции: так ловится предпроверка, у которой обычные отказы до ветки с утечкой не доходят.
4. **«Нет зависших транзакций».** После всего этого в базе не должно быть сессий в `idle in transaction` и сессий, ожидающих блокировку. Так ловится утечка, слишком медленная, чтобы успеть исчерпать пул.
5. **«Данные переживают перезапуск сервиса».** Остаток товара 7 до и после перезапуска сервиса должен совпасть: заказы хранятся в базе, а не в памяти процесса.

Подсказка про больший пул привязана к признаку в системе (зависшие транзакции после нагрузки), а не к проверке, где случился провал: у большого пула ошибок бывает ровно у порога, и провал прыгал бы между нагрузкой и проверкой заказов. Остальные подсказки привязаны к симптому в своей проверке: p95 выше 500 мс — перезапуск, обрывы сессий — таймаут в базе, 503 в гонке за последний товар — проверка остатка до транзакции.

</details>

<details>
<summary>Как не допустить в проде</summary>

- **Правило:** любая транзакция завершается на каждом выходе. `defer tx.Rollback()` сразу после `Begin` и `BeginTx(r.Context(), nil)`, чтобы отмена запроса откатывала транзакцию: по коду он закрывает эту утечку и сам, на стенде не проверялся.
- **Тесты:** интеграционный тест на настоящей базе, который делает больше отказных заказов, чем размер пула, и после них проверяет `db.Stats().InUse == 0`. Одиночный запрос утечку не покажет: она видна только по накоплению.
- **Метрики и алерты:** у Go-клиента `collectors.NewDBStatsCollector` отдаёт `go_sql_in_use_connections` и `go_sql_wait_count_total`. Алерт на `in_use` у максимума при ровном трафике и на рост ожиданий. Со стороны базы — число сессий в `idle in transaction` и время, сколько самая старая из них висит.
- **Страховка в базе:** `idle_in_transaction_session_timeout` на разумный срок (десятки секунд) обрывает забытые транзакции, а алерт на рост `sessions_fatal` показывает, что такие обрывы идут. Без алерта страховка прячет утечку.
- **Kubernetes и облако:** число реплик умножается на размер пула, и сумма должна помещаться в `max_connections` с запасом. Раздутый пул одной реплики оставит без соединений другие сервисы. Перезапуск пода по liveness-пробе лечит симптом так же, как `svc restart`: сбой возвращается. В управляемой базе (RDS, Cloud SQL) таймаут задаётся группой параметров или флагом, а число соединений видно в метриках облака.
- **Линтеры:** `sqlclosecheck` проверяет только `Rows` и `Stmt`, незавершённую `Tx` он не ловит. Здесь поможет тест на пул и привычка ставить `defer tx.Rollback()` сразу после `Begin`.

</details>
