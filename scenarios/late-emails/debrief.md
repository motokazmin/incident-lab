# Разбор: «Письма о заказах опаздывают»

## Что случилось

После каждого заказа сервис кладёт в таблицу `jobs` задачу «отправить письмо». Восемь обработчиков внутри сервиса разбирают эту очередь: берут самую старую задачу, передают письмо почтовому шлюзу (на это уходит около 150 мс) и отмечают задачу выполненной. Всё это происходит в одной транзакции, и задачу обработчик берёт запросом `SELECT … ORDER BY id LIMIT 1 FOR UPDATE`. `FOR UPDATE` блокирует строку до конца транзакции, то есть до `COMMIT`, а `COMMIT` стоит после вызова шлюза.

Поэтому все восемь обработчиков тянутся к одной и той же самой старой строке и встают друг за другом. Это называется head-of-line blocking (затор в голове очереди): пока первый в очереди занят, остальные не могут начать, хотя свободных задач в таблице много. Письма уходят по одному, около 6,5 в секунду (число замерено на учебном стенде), сколько бы обработчиков ни было. В тихое время заказов около 3 в секунду, очередь справляется. Распродажа подняла поток примерно до 12 заказов в секунду, и очередь начала расти на пять-шесть задач каждую секунду. Сайт при этом отвечает без ошибок: письма отправляются в фоне, а клиенту ничего не видно.

Суть починки: не ждать занятую строку, а пропускать её. Быстро это один модификатор `SKIP LOCKED`, надёжнее взять задачу короткой транзакцией и отправлять письмо вне её.

## Что сломано в коде

`queue.go`:

```go
func (s *server) sendNext() (bool, error) {
	tx, err := s.db.Begin()                                  // ① транзакция открыта на всё время отправки
	...
	err = tx.QueryRow(`SELECT id, order_id FROM jobs
		WHERE status = 'new' ORDER BY id LIMIT 1 FOR UPDATE`). // ② всегда самая старая; строка заблокирована до COMMIT
		Scan(&id, &orderID)
	...
	if err := sendMail(orderID); err != nil {                // ③ 150 мс на вызове шлюза, блокировка держится
		return false, err
	}
	if _, err := tx.Exec(`UPDATE jobs SET status = 'sent', ...`, id); err != nil {
		return false, err
	}
	if err := tx.Commit(); err != nil {                      // ④ только здесь блокировка снимается
		return false, err
	}
	...
}
```

По отдельности каждая строка выглядит разумно. `FOR UPDATE` нужен, чтобы два обработчика не взяли одну задачу: это защита от дублей. Самая старая задача первой — честный порядок. Отправка внутри транзакции нужна, чтобы при ошибке шлюза задача откатилась и осталась в очереди. Поломка возникает из сочетания ②, ③ и ④: все обработчики просят одну и ту же строку, а держится она весь сетевой вызов. Защита от дублей превратилась в очередь на одного.

## Как это находится

Путь идёт от симптома к причине, каждый шаг отвечает на один вопрос. В скобках указана ступень подсказок, которая ведёт к тому же шагу.

**1. Ломается сайт или только письма?** (подсказка «Что говорят графики») Ошибок и медленных ответов нет, растёт только третий график: сколько ждёт письма самый старый заказ. Значит, письма уходят медленнее, чем приходят заказы.

**2. С какой скоростью уходят письма?** (подсказка «Что в логах»)
```
grep 'очередь писем' /var/log/shop.log | tail -n 5
```
В `svc logs` эта строка тонет среди запросов, поэтому достаём её из журнала: `очередь писем: отправлено за 10s — N, ждут — M`. Раздели N на 10: получится около 6–7 писем в секунду. Один обработчик, который тратит на письмо 150 мс, отправил бы те же 6–7 в секунду, а восемь параллельных — около 50. Обработчиков восемь, а скорость как у одного.

**3. Очередь растёт?** (подсказка «Сколько ждёт»)
```
psql -U postgres -d shop -c "select status, count(*) from jobs group by status"
```
Повтори несколько раз. Счётчик `new` растёт: задачи появляются быстрее, чем исчезают. Это подтверждает шаг 2, но не говорит, почему.

**4. Что делают обработчики?** (подсказка «Чем заняты обработчики»)
```
psql -U postgres -d shop -c "select pid, state, wait_event_type, wait_event, left(query, 50) from pg_stat_activity where datname = 'shop' and query like '%jobs%' and pid <> pg_backend_pid()"
```
Одно соединение в состоянии `idle in transaction`: оно держит транзакцию открытой и в этот момент ждёт ответа шлюза, а не базы (`wait_event = ClientRead`). Остальные имеют `wait_event_type = Lock`: они стоят и ждут чужую блокировку. Работает один, ждут остальные.

**5. Кого они ждут?** (подсказка «Кто кого ждёт»)
```
psql -U postgres -d shop -c "select pid, pg_blocking_pids(pid) from pg_stat_activity where wait_event_type = 'Lock'"
```
В скобках `{…}` перечислены `pid` тех, кто держит блокировку. Цепочки сходятся к соединению из шага 4 в `idle in transaction`: одни ждут его напрямую, другие стоят за соседом, который уже встал в очередь. Значит, все ждут один захват.

**6. На чём они стоят?** (подсказка «Почему они ждут») Открой `queue.go` и найди запрос, который выполняют ждущие соединения. В нём `ORDER BY id LIMIT 1 FOR UPDATE`: все просят самую старую строку, и она заблокирована до `COMMIT`, который стоит после вызова шлюза. Чтобы чинить, осталось узнать, как не ждать занятую строку (подсказка «Как не ждать»).

**7. Почему это началось сегодня?** Код был таким всегда. Пропускной способности очереди хватало на тихий поток в 3 заказа в секунду, она могла разобрать до 6,5. Распродажа подняла поток до 12 заказов в секунду, и запас кончился. Событие дня только вскрыло причину.

## Как чинить

Занятую строку нужно пропускать, а не ждать.

- **Быстро:** добавить `SKIP LOCKED` к выборке. Запрос пропускает строки, которые уже заблокированы другими, и берёт первую свободную, поэтому восемь обработчиков работают параллельно. Дубли исключены: строку, которую взял один, другие не видят. Оговорка: транзакция по-прежнему открыта на время вызова шлюза, и каждое соединение занято и стоит в `idle in transaction` 150 мс на письмо. Если процесс упадёт посреди отправки, транзакция откатится и задача вернётся в очередь, и письмо уйдёт повторно.
- **Эталон:** захватывать задачу коротким оператором `UPDATE … RETURNING` со `SKIP LOCKED`, а письмо отправлять вне транзакции. Соединение занято доли миллисекунды, а не 150 мс. Оговорка: пока письмо уходит, задача в статусе `sending`. Если процесс упадёт, она останется в нём навсегда. В проде для этого нужна аренда: срок, после которого задачу может взять другой обработчик. Здесь её нет, это тема отдельного разбора.

```go
// queue.go: захват коротким оператором, отправка вне транзакции
err := s.db.QueryRow(`UPDATE jobs SET status = 'sending'
	WHERE id = (SELECT id FROM jobs WHERE status = 'new'
		ORDER BY id LIMIT 1 FOR UPDATE SKIP LOCKED)
	RETURNING id, order_id`).Scan(&id, &orderID)
...
if err := sendMail(orderID); err != nil {
	return false, err
}
_, err = s.db.Exec(`UPDATE jobs SET status = 'sent', sent_at = now() WHERE id = $1`, id)
```

## Почему очевидные «починки» не работают

Проверка смотрит на поведение системы: сколько писем принял шлюз за время нагрузки и не получил ли он один заказ дважды. Текст правки она не читает.

- **Перезапуск и больше обработчиков (`workers = 16`):** скорость определяет не число обработчиков, а то, что они выстроены в цепочку за одной строкой. Шестнадцать в ту же цепочку дают те же 6,5 писем в секунду.
- **Убрать `FOR UPDATE`:** ожидание пропадает, но пропадает и защита: два обработчика читают одну и ту же задачу со статусом `new`, и шлюз получает два письма о заказе. То же происходит, если выбирать задачу не в транзакции, а через `s.db`: блокировка снимается сразу после выборки.
- **`NOWAIT`, `lock_timeout` в базе:** ждущий запрос не пропускает занятую строку, а падает с ошибкой, обработчик пишет её в журнал и спит секунду. Работает по-прежнему один, остальные тратят время на ошибки.
- **Закоммитить до отправки, но оставить статус `new` до конца:** блокировка снята, а задача для других ещё свободна. Пока письмо идёт, второй обработчик берёт ту же задачу.
- **Пачка по десять, условный `UPDATE` в длинной транзакции, общая advisory-блокировка:** это тот же затор, только с другим замком. Пачка держит десять строк, пока шлюз по одному принимает письма. `UPDATE … WHERE status = 'new'` в длинной транзакции ждёт `COMMIT` соседа так же, как `FOR UPDATE`. Общая advisory-блокировка (замок по числу, не по строке) вообще пускает в транзакцию одного обработчика.
- **`idle_in_transaction_session_timeout` в базе:** база обрывает соединение держателя, пока тот ждёт шлюз. Транзакция откатывается, задача остаётся `new`, письмо о ней уже ушло и уходит снова и снова. Скорость не растёт, зато шлюз получает повторы.
- **Отправить письмо прямо при оформлении заказа:** очередь больше не нужна, но покупатель на кассе ждёт шлюз, около 150 мс на каждый заказ. Письмо не должно задерживать оформление.
- **Пометить всё `sent` или не отправлять письмо:** очередь опустеет, а письма не уйдут. Шлюз, а не таблица `jobs`, считает, что получил. Третий график после такой правки не вернётся к нулю даже при верной починке: тем заказам письма уже не уйдут.

## Правило на будущее

> Растёт очередь → с какой скоростью она разбирается → сколько обработчиков реально работает, а сколько ждёт → кого они ждут.
> Блокировка на время сетевого вызова ≠ защита от дублей: защиту даёт короткий захват, а занятую строку можно пропустить.

- **shop** — наш сервис. `POST /orders` записывает заказ и задачу в `jobs` одной транзакцией. Заказ без задачи или задача без заказа невозможны.

- **Шлюз** — отдельный процесс. Принимает письма параллельно, ведёт журнал, и письмо считается ушедшим, только когда его принял шлюз.
- **Третий график** — сколько секунд ждёт письма самый старый заказ. Его считает не таблица `jobs`, а журнал шлюза, потому что `jobs` меняет код, который ты правишь.

|---|---|---|
| первые 60 с | около 3 в секунду | Очередь успевает: в секунду уходит столько же, сколько приходит. Третий график у нуля. |
| после 60 с (распродажа) | около 12 в секунду | Уходит 6,5, приходит 12. Очередь растёт примерно на пять-шесть задач в секунду, третий график идёт вверх без остановки. |

<summary>Механика по звеньям: от строки кода до письма, которое опоздало</summary>

1. Обработчик A открывает транзакцию и берёт блокировку на самую старую строку `jobs` (`FOR UPDATE`).
2. A передаёт письмо шлюзу. Это 150 мс, транзакция остаётся открытой, строка заблокирована. Соединение при этом ничего не делает: оно ждёт ответа шлюза, и в `pg_stat_activity` это `idle in transaction`.
3. Обработчик B выполняет такой же запрос и упирается в ту же строку. База ставит B в ожидание блокировки (`wait_event_type = Lock`).
4. Обработчики C, D и остальные делают то же самое и встают в очередь за A и B.
5. A выполняет `UPDATE … 'sent'` и `COMMIT`. Блокировка снимается.
6. B просыпается и перепроверяет строку: она теперь `sent`, условие `status = 'new'` не выполняется. База пропускает её и берёт следующую по порядку, но следующую уже заняли.
7. Так обработчики проходят по цепочке: начать своё письмо можно, только когда сосед впереди закончил своё. Параллельно идёт не восемь вызовов шлюза, а один.
8. Скорость — одно письмо за 150 мс с накладными расходами, то есть около 6,5 в секунду. Число обработчиков на неё не влияет: добавленные просто встают в конец цепочки.
9. Поток заказов выше этой скорости, поэтому разница копится в `jobs`, а письма по ним уходят всё позже. Клиент видит успешный заказ, а письмо приходит через минуты или часы.

Шаги 6–7 описывают наблюдаемое поведение. Внутреннее устройство ожидания в PostgreSQL сложнее, но результат на стенде именно такой: письма начинаются по одному.

</details>

<details>
<summary>Теория PostgreSQL: блокировки строк, FOR UPDATE, SKIP LOCKED</summary>

### Блокировки строк
- Блокировка строки живёт до конца транзакции: `COMMIT` или `ROLLBACK`. Если транзакция открыта, пока код ходит в сеть, блокировка держится всё это время.
- `SELECT … FOR UPDATE` блокирует выбранные строки так же, как `UPDATE`: чужая транзакция, которая хочет эти строки, ждёт. Обычные `SELECT` без `FOR` не ждут никогда.
- Ждущий после `COMMIT` не берёт старую версию строки: он перепроверяет условие `WHERE` на новой и берёт следующую подходящую строку. Дублей это не даёт, но и не убирает ожидание.

### `NOWAIT` и `SKIP LOCKED`
- `NOWAIT` — вместо ожидания сразу ошибка `55P03 could not obtain lock on row`. Подходит, когда ждать нельзя и надо сообщить пользователю, а не когда нужно взять любую свободную задачу.
- `SKIP LOCKED` — строки, которые уже заблокированы другими, молча пропускаются. Каждый обработчик получает свою свободную задачу. Для очередей это основной приём.
- Цена `SKIP LOCKED`: порядок обработки перестаёт быть строгим. Если A держит задачу 1, а B берёт задачу 2, то 2 может уйти раньше 1. Для писем о заказах это безразлично, для задач «обработай по порядку» нет.
- Выборку со `SKIP LOCKED` можно вложить в `UPDATE … RETURNING`: задача выбирается и получает статус `sending` одним запросом, блокировка живёт миллисекунды, а письмо уходит уже после неё.

### Индекс для очереди
Выборка `WHERE status = 'new' ORDER BY id LIMIT 1` на таблице с десятками тысяч отправленных задач быстра, только если есть частичный индекс `ON jobs (id) WHERE status = 'new'`. Он содержит только новые задачи, и читать мёртвые строки не приходится. В схеме этого стенда он есть. На замерах стенда с индексом верная починка давала около 52 писем в секунду, без него около 40: запас всё ещё был, но заметно меньше и зависел от того, сколько отправленных задач накопилось.

### Транзакция и сетевой вызов
Держать транзакцию открытой на время вызова чужой системы опасно само по себе: соединение с базой занято и ничего не делает, число соединений ограничено (`max_connections`), а вызов может подвиснуть. Правило: сначала короткий захват, потом сетевой вызов, потом короткая отметка.

</details>

<summary>Все починки: верные с оговорками и ложные с объяснением</summary>

### Верные починки (все проходят проверку)

| правка | почему работает | оговорки |
|---|---|---|
| `FOR UPDATE SKIP LOCKED` | Занятая строка пропускается, обработчики берут разные задачи параллельно. | Транзакция по-прежнему открыта на время вызова шлюза: соединение занято на 150 мс. Строгий порядок не гарантируется. |
| `SKIP LOCKED` при хвосте в 20 000 задач | То же самое. Проверка не зависит от того, сколько накопилось: письма считает шлюз. | Хвост разбирается дольше, и третий график падает медленнее. |
| `UPDATE … RETURNING` со `SKIP LOCKED`, отправка вне транзакции (эталон) | Захват занимает миллисекунды, соединения свободны. | Задача, захваченная упавшим процессом, остаётся в `sending`. Нужна аренда. |
| Короткая транзакция без `SKIP LOCKED` (`UPDATE … RETURNING` с `FOR UPDATE`) | Блокировка держится только на время захвата, а не на время письма, ждут доли миллисекунды. | Ожидание блокировки остаётся, просто короткое. При большой конкуренции `SKIP LOCKED` всё равно лучше. Та же оговорка про упавший процесс. |
| Условный `UPDATE … WHERE status = 'new' RETURNING` без транзакции | Побеждает один обработчик, проигравшие получают пустой результат и повторяют через 200 мс. | Холостые обращения к базе вместо пропуска. Та же оговорка про упавший процесс. |
| `DELETE … RETURNING` со `SKIP LOCKED` | Строка удаляется из очереди при захвате, повторно её взять нельзя. | Теряется история задач. Транзакция с отправкой остаётся длинной. |

### Ложные починки (проверка их ловит)

| попытка | что происходит на самом деле |
|---|---|
| `svc restart` | Код тот же, затор тот же. |
| `workers = 16` | Новые обработчики встают в ту же цепочку за той же строкой. Скорость остаётся около 6,5 писем в секунду. |
| Убрать `FOR UPDATE` | Два обработчика читают одну задачу со статусом `new`, шлюз получает два письма. |
| Выбирать задачу через `s.db`, а не через `tx` | Запрос идёт отдельной транзакцией, блокировка снимается сразу после выборки, до отметки. Дубли. |
| `SKIP LOCKED`, но `COMMIT` до отправки, а статус `sent` после | Блокировки нет, а статус ещё `new`: пока письмо идёт, другой обработчик берёт ту же задачу. Дубли. |
| `NOWAIT` | Ждущий падает с ошибкой вместо пропуска, обработчик спит секунду после ошибки. Скорость почти не растёт, журнал засыпает ошибками. |
| `lock_timeout = '100ms'` в базе | То же, что `NOWAIT`, только через 100 мс: запрос отменяется ошибкой, обработчик спит. Затор остаётся. |
| Общая advisory-блокировка в начале транзакции | Та же очередь на одного, только замок другой. |
| Условный `UPDATE … AND status = 'new'` в длинной транзакции | Проигравший ждёт `COMMIT` соседа, потом получает пустой результат. Параллельности нет, плюс холостые циклы. |
| Пачка из 10 задач под `FOR UPDATE` с отправкой по одной | Первый держит десять строк, пока отправляет десять писем по 150 мс. Остальные ждут всю пачку. |
| `idle_in_transaction_session_timeout = '10ms'` в базе | База рвёт сессию держателя посреди отправки. Транзакция откатывается, задача остаётся `new`, а письмо о ней уже ушло: его отправляют снова и снова. Скорость не растёт, у шлюза появляются повторные письма. |
| Отправить письмо в `POST /orders` (`sendMail` при оформлении) | Очередь не нужна, но каждый заказ ждёт шлюз 150 мс: p95 оформления выходит за порог. |
| Отметить задачу выполненной без отправки (убрать `sendMail`) | Очередь не растёт, а шлюз писем не получает. Письма считает шлюз, а не таблица. Третий график останется выше нуля и после верной починки: тем заказам письма не уйдут. |
| `UPDATE jobs SET status = 'sent' WHERE status = 'new'` и код прежний | Хвост списан без писем, новые заказы по-прежнему идут по одному. Эти заказы так и не получат письмо, и график отставания останется высоким даже после верной починки. |


</details>

<details>
<summary>Что проверка не ловит</summary>

Проверка судит по поведению за короткое окно, а не по тексту правки, поэтому часть приёмов в стенд не вошла как отдельный случай. Поведение проверки на них не проверялось, ниже только то, что следует из устройства приёма.

- **`go sendMail(...)` после `COMMIT`:** отправка не держит транзакцию и не задерживает обработчик. Скорость вырастет. Плата в другом: письмо уходит без гарантий, при падении процесса оно теряется или ждёт без учёта.
- **Раскладка `id % W`:** каждый обработчик берёт свои задачи. Обработчики не делят одну строку, но доля остановленного обработчика не разбирается.
- **`OFFSET n` с номером обработчика:** смещение считается по очереди, которая меняется между запросами, поэтому надёжной раскладки по строкам оно не даёт.
- **`ORDER BY random()`:** обработчики реже сталкиваются, но выборка сортирует всю очередь, и при длинном хвосте это дорого. При короткой очереди столкновения возвращаются.
- **Параллельная отправка пачки внутри транзакции:** письма пачки уходят параллельно, но блокировка держится, пока не уйдёт самое медленное из них.
- **`pg_try_advisory_xact_lock(id)` без `FOR UPDATE`:** обработчики пропускают занятые задачи, но пока блокировка не взята, статус ещё читается без защиты, и два обработчика могут взять одну задачу. Дубли редки и вероятностны, поэтому проверка почти всегда видит «пройдено». Ошибка при этом остаётся в коде.

Если твоя правка прошла проверку, это не доказывает, что она верна: перечитай её на дубли, потерю писем при падении и поведение при длинном хвосте.

</details>

<details>
<summary>Как устроена проверка починки</summary>

Проверка смотрит на то, что принял почтовый шлюз, а не на таблицу `jobs`: её меняет учебный код, и ей нельзя верить.

1. **«Письма успевают за потоком заказов, оформление их не ждёт».** Десять секунд идёт поток по 40 заказов в секунду, затем две секунды на письма, ещё не ушедшие. Из счётчиков шлюза берётся прирост принятых писем. Должно быть не меньше 200: сломанная очередь отправляет за это время около 80, верная 400 и больше. Одновременно проверяется само оформление: доля ошибок не выше 1% и p95 не выше 130 мс (синхронная отправка даёт 150 и больше), иначе письмо задерживает покупателя. Если шлюз почти не получил писем, подсказка указывает на отправку. Если писем мало, но среди них есть повторные, подсказка указывает на повторы, а не на скорость.
2. **«О каждом заказе уходит одно письмо».** Тот же поток. Шлюз считает три числа: сколько писем принято, по скольким заказам письмо пришло повторно и сколько всего было повторных писем. Проверка судит по повторным письмам: хотя бы одно — провал. Так ловятся починки, убравшие блокировку вместе с защитой.

Проверка не требует строгого порядка писем и не требует нуля ожиданий на блокировках. Она не зависит от того, сколько задач накопилось к моменту починки.

</details>

<details>
<summary>Как не допустить в проде</summary>

- **Правило:** транзакция с блокировкой строки не должна содержать сетевых вызовов. Сначала короткий захват, потом отправка, потом короткая отметка. Очередь в базе разбирается `FOR UPDATE SKIP LOCKED`, а не `FOR UPDATE`.
- **Тесты:** нагрузочный тест очереди с несколькими обработчиками, который сравнивает скорость с одним обработчиком. Если число обработчиков не меняет скорость, где-то общий замок.
- **Метрики и алерты:** возраст самой старой задачи в очереди (`now() - min(created_at)`) и глубина очереди. Алерт на возраст, а не на число ошибок: ошибок у такой поломки нет. Для PostgreSQL в облаке смотри ожидания `Lock:transactionid` в Performance Insights или `pg_stat_activity`.
- **Признак в Kubernetes и облаке:** подов-обработчиков становится больше, а скорость разбора не растёт. Если вместе с этим в базе растёт число соединений в `idle in transaction`, обработчики держат транзакции открытыми во время сетевых вызовов.
- **Если задачи не должны теряться:** добавь аренду (срок, по истечении которого задачу может взять другой обработчик) и идемпотентность у получателя. Это решает то, чего `SKIP LOCKED` не решает: что будет, если обработчик упал на полпути.

</details>
