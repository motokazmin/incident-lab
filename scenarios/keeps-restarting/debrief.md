# Разбор: «Ошибки приходят волнами»

## Что случилось

Карточка товара просила рекомендации у чужого сервиса и ждала их не дольше 150 мс. Запрос шёл в отдельной горутине (лёгком потоке Go), а результат возвращался через небуферизованный канал: отправка в такой канал ждёт, пока кто-то примет значение. Если рекомендации опаздывали, обработчик отвечал клиенту без них и уходил, а горутина навсегда оставалась ждать получателя и держала в памяти около 0,5 МБ данных. После рассылки популярные товары, которым рекомендации считаются 400 мс, стали открывать часто. Таких горутин набирались сотни, и память упиралась в лимит cgroup — группы процессов с жёстким лимитом памяти, так в Kubernetes работает `limits.memory`. Ядро убивало процесс, супервизор (программа, которая поднимает упавший процесс) запускал его заново, и всё повторялось.

Утечку снимает одна строка, `make(chan recsResult, 1)`, но брошенный вызов при этом всё равно идёт до конца. Надёжнее убрать горутину и отменять сам вызов через контекст.

## Что сломано в коде

`products.go`:

```go
const recsTimeout = 150 * time.Millisecond

ch := make(chan recsResult)              // ① небуферизованный канал
go func() {                              //   строка 35
    cands, err := fetchCandidates(id)    // ② вызов без контекста: таймаута нет
    ch <- recsResult{cands, err}         // ③ строка 37: отправка ждёт получателя — вечно
}()
recs := []int{}
select {
case res := <-ch:
    ...
case <-time.After(recsTimeout):          // ④ обработчик уходит, больше никто не читает ch
    log.Printf("recommendations timeout product=%d", id)
}
writeJSON(...)
```

По отдельности каждая строка выглядит разумно: «карточка не должна ждать рекомендаций», комментарий об этом даже есть в коде. Поломка возникает из сочетания ① и ④. У небуферизованного канала отправка завершается только в момент, когда кто-то принимает значение. После ④ принимать некому, поэтому ③ не завершится никогда.

## Как это находится

Путь идёт от симптома к причине, каждый шаг отвечает на один вопрос. В скобках указана ступень подсказок, которая ведёт к тому же шагу, если ты её открывал.

**1. Сервис падает или тормозит?** (подсказка «Что говорят графики») `svc status`: счётчик перезапусков растёт, хотя ты ничего не перезапускал. Значит, процесс умирает.

**2. Как именно он умер?** (подсказка «Что в логах»)
```
svc logs 2000 | grep -v status=
```
Ищи строку супервизора: `завершился: сигнал KILL, код 137`. SIGKILL процесс сам себе не шлёт: `log.Fatal` дал бы код 1, паника — код 2. Значит, процесс убил кто-то снаружи.

**3. Кто убил?** (подсказка «Кто убил процесс»)
```
dmesg | grep -i 'out of memory'
```
Слова `Memory cgroup` важны: процесс упёрся в лимит своей группы, а не в память всей машины.

**4. Память растёт, пока процесс жив?** (подсказка «Куда уходит память»)
```
watch -n 5 cat /sys/fs/cgroup/shop/memory.current
```
Если память растёт без провалов вплоть до перезапуска, значит, что-то держит её живой.

**5. Что именно копится?** (подсказка «Что копится») Для сервиса на Go первым делом смотри горутины:
```
curl -s 'localhost:6060/debug/pprof/goroutine?debug=1' | head -n 12
```
Почти все горутины стоят в одном месте, и их число растёт между двумя замерами. Это классическая утечка горутин.

**6. Почему они стоят?** (подсказка «Где застряли горутины»)
```
curl -s 'localhost:6060/debug/pprof/goroutine?debug=2' | grep -A 4 'chan send' | head
```
`chan send` означает, что горутина ждёт получателя. Создал её обработчик `getProduct`, а он отвечает клиенту через 150 мс и завершается. Горутин же сотни, и их становится больше. Значит, они пережили своего получателя.

**7. Почему это началось сегодня?** (подсказка «Что произошло с запросом»)
```
svc logs 2000 | grep 'recommendations timeout'
```
Таймауты почти только у товаров с id от 1 до 20, и после рассылки их стало много. Утечка была в коде всегда, но раньше популярные товары открывали редко. Рассылка изменила смесь запросов, а не код.

## Как чинить

Горутина должна уметь завершиться, даже если её никто не ждёт.

- **Быстро:** буфер на одно значение, `make(chan recsResult, 1)`. Отправка всегда завершается, горутина выходит, данные становятся мусором. Оговорка: брошенный вызов всё равно идёт до конца и нагружает чужой сервис.
- **Эталон:** синхронный вызов с `context.WithTimeout`. Горутины и канала нет. Через 150 мс соединение закрывается, `fetchCandidates` возвращает ошибку, ресурсы освобождаются сразу. Обработчик сам владеет своей работой, и ничего не живёт дольше запроса.

```go
// recs.go
func fetchCandidates(ctx context.Context, product int) ([]candidate, error) {
    req, err := http.NewRequestWithContext(ctx, http.MethodGet, fmt.Sprintf(recsURL, product), nil)
    if err != nil {
        return nil, err
    }
    resp, err := http.DefaultClient.Do(req)
    ...
}

// products.go
ctx, cancel := context.WithTimeout(r.Context(), recsTimeout)
defer cancel()
recs := []int{}
if cands, err := fetchCandidates(ctx, id); err != nil {
    log.Printf("recommendations product=%d: %v", id, err)
} else {
    recs = topN(cands, 5)
}
```

Таймаут здесь привязан к `r.Context()`, поэтому если клиент ушёл раньше, вызов тоже отменится.

## Почему очевидные «починки» не работают

Проверка смотрит на поведение системы, а не на текст правки, поэтому все эти попытки она ловит.

- **`SetMemoryLimit`, `SetGCPercent`, любые настройки GC:** они меняют только то, как часто запускается сборщик мусора. А сборщик освобождает лишь память, на которую никто не ссылается. Данные застрявших горутин лежат в их переменных: горутина жива, значит, данные считаются используемыми. Как часто ни запускай сборку, эта память не освободится. Более частая сборка лишь уменьшает запас сверх живых данных: OOM отодвигается, но не отменяется, а процессор при этом занят сборками.
- **Снять лимит памяти:** утечка давит на всю машину. Ещё до OOM ядро вытесняет кэш и код соседних процессов, и тормозит всё. В Kubernetes под давлением памяти kubelet вытесняет уже чужие поды. Проверка требует, чтобы лимит был на месте.
- **Урезать ответ:** горутина держит меньше памяти, но горутины копятся. OOM наступит позже, а не исчезнет.
- **Контекст в `fetchCandidates`, но отправка в канал прежняя:** вызов отменяется и быстро возвращает ошибку, но горутина всё равно встаёт на `ch <- {nil, err}`. Утекают лёгкие горутины, утечка осталась.
- **Ждать дольше или без таймаута; убрать рекомендации совсем:** либо карточка ждёт чужой сервис (медленный ответ клиенту — тоже отказ), либо пропала сама функция.

## Правило на будущее

> Перезапуски с кодом 137 → OOM → растёт ли память, пока процесс жив → что копится (в Go сначала горутины) → где они стоят и кого ждут.
> «Таймаут на ожидание» ≠ «отмена работы»: работу останавливает только контекст.

<details>
<summary>Механика по звеньям: от горутины до KILL</summary>

1. Популярному товару сервис рекомендаций отвечает за 400 мс, а обработчик ждёт 150 мс и отвечает клиенту без рекомендаций. Для клиента всё в порядке.
2. Горутина продолжает работать: дожидается ответа, читает около 490 КБ JSON и раскладывает его в `[]candidate`. Получается 1000 × 64 × 8 байт ≈ 512 КБ одних признаков.
3. Горутина встаёт на `ch <- …`. Сборщик мусора освобождает только то, до чего нельзя добраться из работающего кода, а стек живой горутины — как раз такой работающий код. `cands` лежит в её локальных переменных, поэтому эти полмегабайта живые, и GC их не соберёт.
4. Горутина, которая заблокирована навсегда, для рантайма Go ничем не отличается от той, что просто долго ждёт. Рантайм не завершает и не собирает такие горутины. Ошибка `all goroutines are asleep - deadlock!` срабатывает, только когда спят все горутины, а в живом сервере так не бывает никогда.
5. `memory.current` в cgroup растёт. Когда он доходит до `memory.max`, ядро сначала пытается вернуть память (page cache и прочее). Не получается — внутри cgroup запускается OOM killer и выбирает жертву. Здесь это `shop`.
6. Процесс получает SIGKILL. Перехватить его нельзя, поэтому не срабатывают ни `defer`, ни graceful shutdown. Код выхода 137 = 128 + 9 (номер SIGKILL).
7. Запросы, которые были в обработке, обрываются. Новые получают отказ в соединении, пока супервизор не поднимет процесс. Это и есть всплеск ошибок.
8. Новый процесс стартует с пустой памятью, и цикл повторяется.

</details>

Если бы она росла скачком на одном запросе, это был бы другой класс проблем: огромный ответ или выгрузка всей таблицы в память.

**Шаг 5, горутины.**
```
goroutine profile: total 387
371 @ 0x... 0x... 0x...
#	0x...	main.(*server).getProduct.func1+0x...	…/products.go:37
```
`371 @` означает 371 горутину с одинаковым стеком. `func1` — первое анонимное замыкание внутри `getProduct`, то есть `go func() {...}`, а строка 37 — отправка в канал.

**Шаг 6, где стоят.**
```
goroutine 5121 [chan send]:
main.(*server).getProduct.func1()
	…/products.go:37 +0x...
created by main.(*server).getProduct in goroutine 5098
	…/products.go:35 +0x...
```
`chan send` — состояние: горутина ждёт получателя. `created by` показывает, кто её запустил: обработчик `getProduct`. Если горутина ждёт дольше минуты, Go допишет время (`[chan send, 3 minutes]`). В сервисе, который течёт медленно, эти минуты — самый быстрый признак утечки.

**Про профиль `heap`.** Он здесь вторичен. Он покажет, что память выделена в `encoding/json` внутри `fetchCandidates`, но не скажет, почему она не освобождается. Ответ на это «почему» даёт профиль `goroutine`.

<details>
<summary>Теория Go: каналы, утечка горутин, select, контекст, GC, pprof</summary>

### Каналы в Go
- **Небуферизованный** канал `make(chan T)` — это рандеву: отправка и приём завершаются одновременно, и каждая сторона ждёт другую.
- **Буферизованный** канал `make(chan T, n)`: отправка завершается сразу, пока в буфере есть место. Буфер на одно значение при одном отправителе гарантирует, что отправка никогда не заблокируется.
- Канал без читателей сборщик мусора уберёт, только когда на него никто не ссылается. Но заблокированная горутина ссылается на него сама, поэтому и горутина, и канал, и всё, что на них ссылается, остаются живыми.

### Утечка горутин
Утечкой горутины называют горутину, которая не может завершиться, потому что ждёт событие, которое больше не наступит. Типичные случаи:
- отправка в канал, из которого больше никто не читает (наш случай);
- чтение из канала, который никто не закроет;
- вызов без таймаута к зависимости, которая не отвечает;
- `select` без ветки `ctx.Done()`.

Каждая горутина стоит как минимум 2–8 КБ стека, плюс всё, что достижимо из её переменных. Здесь основной вес — данные, а не стек.

### `select` с таймаутом не отменяет работу
`case <-time.After(d)` ограничивает только то, сколько обработчик ждёт результат. Сама работа в горутине продолжается: HTTP-запрос идёт до конца, ответ читается и декодируется. Таймаут в `select` отвечает на вопрос «сколько я готов ждать», но не означает «прекрати». Работу останавливает только отмена, а в Go отмену передаёт `context.Context`.

### Контекст в `net/http`
- `http.NewRequestWithContext(ctx, …)`: когда `ctx` отменяется, клиент закрывает соединение, а `Do` сразу возвращает `context deadline exceeded` или `context canceled`.
- `r.Context()` у входящего запроса отменяется, когда клиент разорвал соединение или обработчик вернул управление. Поэтому ветка `case <-r.Context().Done()` в горутине — надёжный признак, что результат больше не нужен.
- `http.Get` и `http.DefaultClient` не ограничивают ожидание ответа: таймауты есть только на установку соединения, а зависимость, которая зависла, держит вызов вечно. В проде это отдельный риск.

### Сборщик мусора, `GOGC` и `GOMEMLIMIT`
- GC освобождает только недостижимую память. Утечка горутин — это достижимая память, поэтому никакие настройки GC её не вернут.
- `GOGC=100` позволяет куче вырасти до размера живых данных плюс ещё столько же до следующей сборки. Поэтому OOM наступает раньше, чем живые данные дойдут до 256 МиБ.
- `GOMEMLIMIT` заставляет GC работать чаще у порога. При настоящей утечке GC у порога работает почти непрерывно и забирает до половины процессора (больше не даёт ограничитель рантайма). Задержки растут, а потом память всё равно упирается в `memory.max`, и наступает OOM.

### pprof
- `goroutine?debug=1` группирует горутины с одинаковым стеком, самые большие группы идут первыми. Это лучший вид для поиска утечки.
- `goroutine?debug=2` показывает каждую горутину отдельно, с состоянием (`chan send`, `chan receive`, `select`, `IO wait`), а от минуты ожидания — и с его временем.
- `heap` показывает, где выделена живая память, а `allocs` — где выделялось вообще.
- В проде профиль снимают через `go tool pprof http://…/debug/pprof/goroutine`. Сравнение двух снимков (`-base`) показывает, что прибавилось.

</details>

<details>
<summary>Теория ОС: cgroup, OOM killer, код 137 и перезапуски</summary>

### cgroup v2 и OOM killer
- `memory.max` — жёсткий лимит группы, `memory.current` — сколько используется сейчас, `memory.events` — счётчики, среди них `oom_kill`.
- Лимит учитывает анонимную память процесса (кучу Go, стеки) и page cache, причём cache ядро может вытеснить, а кучу без swap — нет (swap здесь нет).
- OOM внутри cgroup убивает процесс из этой группы, машина при этом остаётся жива. В Kubernetes `resources.limits.memory` превращается ровно в это, а убитый контейнер получает `OOMKilled` и `exit code 137`.

### Код выхода 137 и перезапуски
- `128 + N` означает, что процесс завершён сигналом N. 137 — это SIGKILL (9), 143 — SIGTERM (15).
- Супервизор (systemd `Restart=always`, kubelet) поднимает процесс заново. В Kubernetes это растущий `RESTARTS` и затем `CrashLoopBackOff`. Перезапуск прячет утечку, поэтому график показывает волны, а не ровную деградацию.

</details>

<summary>Все починки: верные с оговорками и ложные с объяснением</summary>

### Верные починки (все проходят проверку)

| правка | почему работает | оговорки |
|---|---|---|
| `make(chan recsResult, 1)` | Отправка всегда завершается, горутина выходит, данные становятся мусором. | Брошенный вызов всё равно идёт до конца: держит соединение с чужим сервисом, пока тот не ответит, а потом читает и разбирает ответ, который никому не нужен. Вырастет нагрузка или задержка — упрётся и это. |
| `select { case ch <- res: case <-r.Context().Done(): }` | Горутина узнаёт, что получателя больше нет, и выходит. | Те же, что у буфера: сам вызов не отменяется. |
| После таймаута `go func() { <-ch }()` | Получатель появляется всегда. | Работает, но добавляет ещё одну горутину на каждый таймаут. Это латание, а не модель. |
| Неблокирующая отправка `select { case ch <- res: default: }` | Горутина никогда не ждёт. | Корректность держится на тайминге: если вызов завершится раньше, чем обработчик дойдёт до `select`, результат потеряется. Здесь вызов идёт минимум 20 мс по сети, поэтому на практике это незаметно, но в общем случае так делать не стоит. |
| **Синхронный вызов с `context.WithTimeout`** | Горутины и канала нет. Через 150 мс соединение закрывается, `fetchCandidates` возвращает ошибку, ресурсы освобождаются сразу. | Эталон. Обработчик сам владеет своей работой, и ничего не живёт дольше запроса. |

### Ложные починки (проверка их ловит)

| попытка | что происходит на самом деле |
|---|---|
| `debug.SetMemoryLimit`, `SetGCPercent(10)` | Меняют только частоту сборки мусора. Данные застрявших горутин лежат в их переменных и считаются используемыми, поэтому сборщик их не освободит. Меньше запас сверх живых данных — OOM отодвигается, но не отменяется, а процессор занят сборками. |
| Снять лимит (`echo max > memory.max`) или вынести процесс из cgroup | Утечка давит на всю машину: ещё до OOM ядро вытесняет кэш и код соседей, тормозит всё. В Kubernetes под давлением памяти kubelet вытесняет уже чужие поды. Проверка требует, чтобы лимит был на месте. |
| Урезать ответ в горутине до 5 кандидатов | На горутину приходится меньше памяти, но горутины копятся. OOM наступит позже, а не исчезнет. |
| Контекст в `fetchCandidates`, но отправка в канал прежняя | Вызов отменяется и быстро возвращает ошибку, но горутина всё равно встаёт на `ch <- {nil, err}`. Утекают лёгкие горутины, утечка осталась. |
| Закрыть канал после таймаута (`close(ch)` в ветке таймаута) | `close` будит застрявшего отправителя, и тот паникует: `panic: send on closed channel`. Если вызов ещё не дошёл до отправки, паника случится, когда дойдёт. Паника происходит в нашей горутине, а не в горутине обработчика, `recover` из `net/http` её не ловит, и процесс падает с кодом 2 на первом же опоздавшем ответе. Да и закрывать канал не нужно: сборщик мусора собирает открытый канал так же, как закрытый, если на него никто не ссылается. |
| Буфер плюс таймаут 1 с (с запасом над 400 мс популярных), или ждать без таймаута | Утечки нет, но карточка ждёт чужой сервис: когда он отвечает 2 с, карточка опаздывает на секунду. Медленный ответ клиенту — тоже отказ. |
| Убрать рекомендации совсем | Утечки нет, но и функции нет. |

</details>

<details>
<summary>Как устроена проверка починки</summary>

Проверка смотрит на поведение системы, а не на текст правки:

1. **«Карточки открываются, даже когда рекомендации тормозят».** Сервис рекомендаций переводится в режим «2 с на любой товар», затем 25 с идёт нагрузка 40 запр/с по товарам, которых не трогал фон. За это время не должно случиться ни одного перезапуска и ни одного OOM, доля ошибок должна быть не выше 0,5%, p95 — не выше 300 мс. Перед нагрузкой проверяется, что лимит памяти на месте.
2. **«Горутины не копятся».** 10 с медленной нагрузки, 3 с паузы (брошенные вызовы длятся 2 с), после этого в коде сервиса должно остаться не больше 3 горутин. Так ловится утечка, слишком медленная, чтобы успеть дойти до OOM: урезанный ответ, контекст без `select`.
3. **«У карточек есть рекомендации».** Идёт в том же процессе после медленной нагрузки. Рекомендации сверяются с ожидаемыми, поэтому заглушка вместо них не пройдёт.

</details>

<details>
<summary>Как не допустить в проде</summary>

- **Правило:** горутина, запущенная в обработчике, должна иметь гарантированный выход, который не зависит от того, дождался ли её кто-то. Если гарантию не сформулировать, горутина не нужна.
- **Тесты:** `go.uber.org/goleak` — `defer goleak.VerifyNone(t)` в тесте обработчика с медленной заглушкой зависимости. В Go 1.26 появился экспериментальный профиль `goroutineleak` (`GOEXPERIMENT=goroutineleakprofile`): он находит ровно такие горутины — заблокированные на канале, до которого больше никто не дотянется.
- **Метрики:** алерт на рост `go_goroutines` (Prometheus client отдаёт её по умолчанию), если число растёт при ровном трафике. Ещё один сигнал — `container_memory_working_set_bytes` рядом с лимитом.
- **Признак в Kubernetes:** растущий `RESTARTS` вместе с `Last State: Terminated, Reason: OOMKilled` почти всегда означает утечку, а не «мало памяти».
- **Клиенты к зависимостям:** у `http.Client` всегда задавать `Timeout`, а каждый вызов делать с контекстом запроса.

</details>
