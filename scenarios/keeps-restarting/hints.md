## Что говорят графики

Ошибки идут всплесками, между ними всё работает. Похоже, сервис на короткое время пропадает целиком. Посмотри, жив ли он: `svc status`. Строка «перезапусков с начала» — счётчик, сверься с ним ещё раз позже. Пока смотришь, сам не перезапускай: счётчик считает и твои перезапуски.

## Что в логах

Строки запросов заглушают остальное. Посмотри только сообщения самого сервиса:

```
svc logs 2000 | grep -v status=
```

Найди строку супервизора о перезапуске. Каким сигналом завершён процесс? Команда не заканчивается сама, останови её Ctrl+C.

## Кто убил процесс

Сигнал KILL сервис сам себе не шлёт. Спроси ядро:

```
dmesg | grep -i 'out of memory'
```

## Куда уходит память

Сервис упёрся в память. Посмотри, как меняется занятая память: `watch -n 5 cat /sys/fs/cgroup/shop/memory.current`, выйти — Ctrl+C. Значение в байтах: лимит 256 МиБ — это 268435456. Растёт ли оно, пока сервис живёт?

## Что копится

Go отдаёт профили на служебном порту. Профиль `goroutine` показывает, сколько горутин живо и где каждая стоит, самые большие группы — первыми. Целиком его удобно листать через `| less` (выйти — `q`), начало видно так:

```
curl -s 'localhost:6060/debug/pprof/goroutine?debug=1' | head -n 12
```

Строка вида `N @ …` — N горутин с одинаковым стеком. Возьми группу с самым большим N и прочти функции под ней: верхняя — где горутины стоят сейчас. Для утечки сравни число всех горутин дважды с интервалом в десять секунд: `curl -s 'localhost:6060/debug/pprof/goroutine?debug=1' | head -n 1`.

## Где застряли горутины

Подробнее об одной из них:

```
curl -s 'localhost:6060/debug/pprof/goroutine?debug=2' | grep -A 4 'chan send' | head
```

Покажется несколько горутин, смотри на любую: стеки одинаковые. `chan send` значит «ждёт, пока кто-то примет значение из канала». Открой `products.go` на строке из стека. Что она отправляет и кто должен это принять?

## Что произошло с запросом

В логе сервиса есть строки `recommendations timeout product=…`. Для каких товаров они и как часто? После рассылки таких запросов стало много: обработчик уходит по таймауту, а горутина навсегда остаётся ждать на небуферизованном канале и держит в памяти полученных кандидатов.

## Готовая правка

Дай горутине завершиться, даже если её никто не ждёт. Проще всего — буфер на одно значение: `make(chan recsResult, 1)`. Надёжнее — отменять сам вызов: `context.WithTimeout` и `http.NewRequestWithContext`, а вызов делать прямо в обработчике, без горутины и канала. Если горутину оставишь, ей всё равно нужно куда-то отправить результат, не дожидаясь получателя. Потом сохрани файл, выполни `svc deploy` и нажми «Проверить починку».
