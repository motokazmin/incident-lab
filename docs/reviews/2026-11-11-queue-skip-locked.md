# Сюжет №60 «Письма о заказах опаздывают» — очередь в базе без SKIP LOCKED

## Контекст

Каталог №60, сложность 2, тип — архитектура. Пара к вышедшему эпизоду 01 Хекслета
(`~/pet-projects/edugo/docs/episodes/01-skip-locked.md`), кейс 1: FOR UPDATE → head-of-line
blocking → SKIP LOCKED. Кейс 2 (аренда, зомби, идемпотентность) — кандидат в продолжение.
Новое для каркаса: асинхронный симптом, которого не видно в HTTP. Разобрано `incident-engineer`
и `scenario-architect` 11.11 (оценки по коду и исходникам PostgreSQL, стендом не проверено).

Готово, когда: сюжет в `scenarios.All()`, алерт по отставанию на стенде ~1 мин после пика,
все случаи `TestRepairs` зелёные в CI на ветке, сюжет пройден в браузере, ADR 0013 и
`docs/architecture.md` обновлены, тексты прошли `methodist` и `incident-engineer`.

## Поломка

`POST /orders` пишет заказ и задачу `jobs` одной транзакцией. В сервисе `WORKERS=8` горутин:

```sql
BEGIN;
SELECT id, order_id FROM jobs WHERE status='new' ORDER BY id LIMIT 1 FOR UPDATE;
-- POST в почтовый шлюз, 150 мс
UPDATE jobs SET status='sent' WHERE id=$1; COMMIT;
```

Все обработчики ждут держателя головы очереди: ~6,4 письма/с при любом `WORKERS`. Ждущий после
COMMIT соседа пропускает строку и берёт следующую (EvalPlanQual) — совпадает с эпизодом.
Улики: рост `count(*) … status='new'`, в `pg_stat_activity` один `idle in transaction` и N−1 в
`Lock/transactionid|tuple`, `pg_blocking_pids` указывает на один PID.

Обязательно в исходном сервисе и образе, иначе шум или ложная «починка»:
- частичный индекс `ON jobs(id) WHERE status='new'` в схеме;
- шлюз отвечает параллельно (Go, `time.Sleep`), таймаут клиента сервиса ≥ 5 с;
- корректное завершение по SIGTERM: перестать брать задачи, дослать текущие;
- пул Go ≥ W + конкурентность HTTP, `max_connections` с запасом.

**Нагрузка (оценка):** тихо 3 заказа/с (ρ≈0,47), `Rise` — пик 12 заказов/с, отставание растёт
на ~5,6/с; верная починка при W=8 даёт ~53/с.

## Шлюз — в папке сюжета

Заглушка `/opt/mail/mail` вне `/srv/app`, запуск из `boot` по образцу
`scenarios/keeps-restarting/image/boot`. Журнал отправок: время, номер заказа. Действия в
`image/actions/`: сводки, а не журнал целиком (предел `agentproto.MaxActionOut`):
`mail-lag` — возраст самого старого заказа без письма; `mail-window <от>` — писем и дублей в окне.

## Каркас: алерт по отставанию (решение пользователя 11.11)

Опрос метрики действием сюжета (A′ `incident-engineer`): каркас раз в 5 с
вызывает `Action(mail-lag)`, разбирает одно число с пределом, порог `Alert.MaxLag`, серия на
третьем графике только у сюжетов с метрикой. Отставание растёт и при полностью вставшей
очереди. Данные из гостя, но алерт — не вердикт (ADR 0004). Переиспользуют №15, 21, 35, 49, 52.

Изменения:
- `platform/scenario/scenario.go`: `Alert.MaxLag`, `Scenario.Lag *Lag{Action, Title}`.
- `platform/internal/lab/lab.go`: опрос вместе с нагрузкой в `startLoad`/`stopLoad`, стоит во
  время проверки; порог в `alertReason` до раннего выхода на `sent == 0`.
- `platform/internal/load`: `Sample.LagMs` (отличим от «нет данных»), запись без `sent++`.
- `web/src/api.ts`, `web/src/main.ts`: необязательная серия, `Chart` уже обобщён.
- Тесты: `TestAlertReason`, опрос стоит при проверке, `scenarios_test.checkAlert` (`MaxLag`
  без `Lag` запрещён). ADR 0013, `docs/architecture.md`.

## Проверки починки

Судим по пропускной способности и дублям из журнала шлюза, не по задержке своих заказов
(за отставанием в 30 тыс. они не успеют за 2 мин проверки) и не по `jobs`/API.
1. **Успевает:** `RunLoad` вливает 400 заказов (порог p95/ошибок на `POST /orders` — ловит
   синхронную отправку); писем за окно 10 с ≥ 200. Сломанный ~64, верный ≥ 400.
2. **Нет дублей:** заказ отправлен ≥ 2 раз, оба раза внутри окна проверки.
3. По желанию — «медленное письмо» с кворумом (ловит параллельную отправку пачки под FOR UPDATE).
Без перезапуска сервиса в проверках; без требования FIFO и нуля ожиданий `Lock`.
Подсказки при провале — по признаку (ожидания на `jobs` ≥ W−1, дубли), не по проверке.

## Починки для e2e (`repairs.go`)

Верной считается любая быстрая починка без дублей (решение пользователя 11.11).

- **Pass:** `SKIP LOCKED` (`AfterAlert`); `UPDATE … RETURNING` + `SKIP LOCKED` и отправка вне
  транзакции; короткая транзакция без `SKIP LOCKED`; CAS autocommit; `DELETE … RETURNING`;
  `SKIP LOCKED` при отставании 20 000 (вставка через `psql`, затем `svc deploy`).
- **Fail:** рестарт; `WORKERS=32`; без `FOR UPDATE`; `db.QueryRow` вместо `tx`; `SKIP LOCKED` с
  COMMIT до отправки без смены статуса; `NOWAIT` с повтором; `lock_timeout`; общая advisory;
  пачка с последовательной отправкой; CAS в длинной транзакции; заглушка без отправки;
  очистка очереди без правки кода.
- Не ловим, разбираем в разборе: `ORDER BY random()`, раскладка `id % W`, `go send()`.

## Замеры 11.11 (одна виртуалка, стенд `pool-exhausted`, сервис заморожен, отправка — `pg_sleep(0.15)` в транзакции)

| вариант | W | очередь | писем/с |
|---|---|---|---|
| FOR UPDATE, частичный индекс | 1, 4, 8, 16 | 3000 | 6,5 (131 за 20 с при любом W) |
| SKIP LOCKED, частичный индекс | 8 | 30 тыс. новых за 30 тыс. отправленных | 52 |
| SKIP LOCKED, без индекса | 8 | то же | 40 |
| FOR UPDATE, без индекса | 8 | то же | 6,5 |

Перепроверка (три сессии `psql`, держат строку 1 с): при 10 новых A→1, B→2 через 1 с, C→3
через 2 с — по одной, как в эпизоде; при одной строке B и C получают пустой результат.
Вывод: числа плана подтверждены, частичный индекс оставить в схеме (без него запас верной
починки 40/с вместо 52/с и зависит от возраста стенда). Прогон сорвался в первый раз:
`pool-exhausted` по своему сюжету выбирает `max_connections`, сервис пришлось заморозить.

## Стенд 11.11: e2e и снимок вывода

- e2e по одному на ноутбуке: «без починки» — алерт через 2:07, шлюз принял 79 писем при пороге 200;
  «SKIP LOCKED» после алерта — 620; «эталонный путь», «без FOR UPDATE» (79 заказов с повтором),
  «больше обработчиков» (78), `idle_in_transaction_session_timeout` (88 писем, 87 повторных),
  «письмо при оформлении заказа» (p95 156 мс) — как ожидалось.
- «Эталонный путь» сначала упал: `svc logs` показывает последние 50 строк, при 40 запросах/с это меньше
  2 с, строка «очередь писем» раз в 10 с туда не попадает. Шаг заменён на
  `grep 'очередь писем' /var/log/shop.log | tail -n 5`, в подсказке тоже.
- Разбор `incident-engineer` после проверок: повторы считаются письмами, а не только новыми заказами
  с повтором (иначе `idle_in_transaction_session_timeout` шлёт одно письмо раз за разом незаметно);
  при провале скорости с повторами подсказка про повторы; порог p95 оформления 130 мс; Expect шага 4 —
  `Lock`; отметка `mail-lag` с запасом 1000 номеров.
- Снимок через полторы минуты после распродажи: семь ждущих в `Lock/transactionid` (не `tuple`), держатель
  `idle in transaction`/`ClientRead`; `pg_blocking_pids` даёт цепочки — пятеро ждут держателя, двое ждут
  третьего, который ждёт держателя. Вывод вставлен в разбор.
