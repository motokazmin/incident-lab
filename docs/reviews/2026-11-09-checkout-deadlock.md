# Сюжет №4: дедлок в базе (каталог №3) — замысел

Черновик до кода, 09.11. Выбор сюжета — решение пользователя 09.11.

## Поломка

Сервис магазина, PostgreSQL. Ручка «Повторить заказ»: `POST /orders/{id}/repeat`. Прошлые заказы
лежат в базе (`order_items` с `position` — порядок, в котором покупатель добавлял товары). Сервис
открывает транзакцию и по позициям в порядке `position` делает
`UPDATE products SET stock = stock - $1 WHERE id = $2 AND stock >= $1` (строчная блокировка),
потом вставляет новый заказ.

Прошлые заказы засеяны в `schema.sql` детерминированно: много заказов содержат одни и те же
популярные товары в разном порядке (A,B и B,A). Под конкурентной нагрузкой две транзакции берут
блокировки встречно, PostgreSQL через `deadlock_timeout` (1 с) рвёт одну: `40P01 deadlock detected`,
сервис отвечает 500.

Ограничение каркаса: в нагрузке один `{id}` на запрос, поэтому корзина берётся из базы, а не из
тела запроса. Каркас не меняется.

## Что видит дежурный

Название — симптом: «Часть заказов падает». Нагрузка: тихая часть без дедлоков (мало повторов
заказов), затем `Rise` — «распродажа», много повторов популярных наборов. Алерт по доле ошибок
(порог подобрать замером, ожидание 5–10%) и, возможно, по p95 (жертвы и ждущие висят до 1 с).

## Путь диагностики

1. Графики: ошибки только на повторах заказов, часть запросов около 1 с.
2. `svc logs`: `pq: deadlock detected (40P01)` в `repeatOrder`.
3. Журнал базы `/var/log/postgresql.log`: `Process X waits for ShareLock on transaction Y; blocked by
   process Z`, оба запроса — `UPDATE products ...`, `CONTEXT: while updating tuple (…) in relation "products"`.
4. `pg_stat_database.deadlocks` растёт; `pg_locks` во время ожидания.
5. Код: блокировки идут в порядке позиций заказа, у двух заказов порядок встречный.

## Верная починка

Брать блокировки в одном порядке: отсортировать позиции по `product_id` (в Go или `ORDER BY product_id`
в выборке позиций). Варианты: `SELECT ... FROM products WHERE id = ANY($1) ORDER BY id FOR UPDATE`
перед обновлениями.

## Ложные починки (кандидаты)

| Починка | Чем ловим |
|---|---|
| Рестарт | Сбой возвращается на нагрузке |
| Повтор при 40P01 в Go | Ошибок нет, но `pg_stat_database.deadlocks` растёт; каждая жертва стоит 1 с |
| `deadlock_timeout = 10ms` | Ошибки остаются (жертв больше, а не меньше) |
| `lock_timeout` / `NOWAIT` | Ошибки остаются |
| Убрать блокировку/условие `stock >= qty` | Продажа в минус: гонка за последнюю единицу |
| Пул на 1 соединение, глобальный мьютекс | Пропускная способность: p95 на тройной нагрузке. Под вопросом, см. ниже |
| `SERIALIZABLE` | Ошибки сериализации вместо дедлоков |
| Заглушка ручки | Сверка остатков и состава нового заказа |
| Один `UPDATE ... FROM (VALUES ...)` без порядка | Порядок блокировок не гарантирован; поймает ли — замер |

## Проверки (черновик)

1. Тройная нагрузка с повторами пересекающихся наборов: ошибок ≤ порога, p95 ≤ порога, и
   `deadlocks` в `pg_stat_database` не вырос ни на один. Признак в системе, а не в коде.
2. Повтор заказа списывает остаток каждой позиции и создаёт заказ с тем же составом.
3. Последняя единица достаётся одному покупателю (товары с остатком 1 в наборах).
4. Нет зависших транзакций; данные переживают перезапуск.

## Открытые вопросы к инженеру

- Реален ли сюжет «повтор заказа» как источник встречного порядка, или честнее корзина/пакетное
  списание склада? Как это ломается в проде на самом деле.
- Повтор при 40P01 — ложная починка или допустимая? Документация PostgreSQL советует повторять
  транзакции при сериализационных сбоях; для дедлока — устранять причину.
- Глобальный мьютекс и пул на 1: можно ли честно поймать по поведению, не делая транзакцию
  искусственно долгой? Если нельзя — признать их допустимыми или убрать из списка.
- Детерминизм: дедлок зависит от расписания. Доказать замером, что без починки он случается в 100%
  прогонов проверки, а с верной — 0 дедлоков.
- Какие верные решения проверка может ошибочно отвергнуть (например, `SELECT ... ORDER BY id FOR
  UPDATE`, advisory-блокировки в порядке id).

## Разбор incident-engineer, 09.11

Замер в Docker на PG17 из `lab-base`, `--cpus=2`, без HTTP и виртуалки; стенд в scratchpad сессии.

- **Нагрузка даёт фазовый переход, а не долю ошибок.** Равномерно 30–150 rps — 0 дедлоков, 200 rps —
  лавина (528 дедлоков, бэклог не рассосался за 5 мин). Порог алерта по доле ошибок не подобрать.
- **Признак для проверки — залп** одновременных повторов, как `checkLastUnit`: K=16 — дедлок в 15/15
  раундах, K=4 — 9/15; сортировка — 0/15. Нужен замер через `env.Do` и число раундов R с (1−p)^R < 1e-6.
- **Критерий верной починки за залп:** Δ`deadlocks` = 0, Δ`xact_rollback` = 0, `stats_reset` не
  изменился, все ответы 2xx, остатки и состав сходятся. Статистику читать через ≥2 с после залпа,
  `before` — после деплоя и паузы.
- **Дыры черновика:** `lock_timeout`/`NOWAIT` + повтор (0 дедлоков, +1558 откатов) — ловится
  `xact_rollback`; без транзакции — нужен случай «один товар раскуплен → остальные не тронуты, заказа
  нет»; переписать `position` в базе — проверка должна сама создавать встречные заказы через API.
- **`id = ANY`** — порядок физический, вердикт случайный (2/15, затем 0/30).
- **`UPDATE … FROM VALUES`** в порядке корзины — ложная (6/15), отсортированный по id — верная.
- **`SERIALIZABLE`** не заменяет дедлоки ошибками сериализации: 40P01 остаётся, 40001 добавляется.
- **Повтор + сортировка** — верная; повтор без сортировки — ложная (Δ`deadlocks` > 0).
- **Глобальный мьютекс, пул на 1, `pg_advisory_xact_lock(1)`** при транзакции 2–5 мс по поведению не
  ловятся.
- **Журнал:** оба процесса — один `UPDATE` с `$1/$2`, ctid меняется; порядок товаров не виден. Нужны
  `log_lock_waits = on`, `log_parameter_max_length_on_error = -1`, явный `deadlock_timeout` меньше
  HTTP-таймаута сервиса (1 с), иначе клиент получает 503 раньше дедлока. В журнале `while locking tuple`.
  В `svc logs` lib/pq пишет `pq: deadlock detected` без кода.
- Основная масса ошибок в залпе — таймауты (57014), а не 40P01: алерт естественнее по p95.

## Решения пользователя, 09.11

- Симптом: транзакция повтора реалистично длиннее (движение по складу, пересчёт цены по позициям),
  чтобы дедлоки шли потоком на умеренной нагрузке. Режим нагрузки и алерт — замером на виртуалке.
  Вердикт проверки — по залпу. Каркас не меняется.
- Глобальный мьютекс, пул на 1, одна общая advisory-блокировка — допустимые починки (Pass: true в
  `TestRepairs`), разбор объясняет цену: не работает на нескольких репликах, упирается в пропускную
  способность.
- `id = ANY` в `TestRepairs` не включаем: вердикт недетерминирован. Упомянуть в разборе.

## Замер нагрузки, 09.11

e2e на виртуалке, популярных товаров 3, транзакция ~2 мс: алерта нет за 4 мин ни при 30/40, ни при 40/50
(rps/% повторов). Залп проверки при этом надёжен: сломанный код — 91–122 дедлока за проверку, сортировка — 0
дедлоков и 0 откатов.

Транзакция удлинена скидкой постоянному покупателю (`count(*)` по истории без индекса после блокировки
товара), история — 30 000 заказов. Docker на образе стенда, `--cpus=2 --memory=1g`, равномерная нагрузка:

| rps/% повторов | сломанный код | сортировка |
|---|---|---|
| 25/40, 30/40, 35/45 | 0 дедлоков за 60–90 с (однажды всплеск 7 и затухание) | — |
| 40/50 | 4 из 4: лавина за 10 с, через минуту 97% ошибок, ~700 дедлоков | 0 ошибок, 0 дедлоков |

В лавине падают и чтения: `getOrder`/`getProduct: context deadline exceeded` — пул занят жертвами и
ждущими. Плавного режима «часть заказов падает» при равномерной нагрузке нет.

## Решение пользователя и разбор scenario-architect, 09.11

Пользователь: всплески в каркасе (пуш «повтори заказ», N клиентов разом). Разбор архитектора, без нагрузки:

- Поле `LoadProfile.Burst *Burst{Every, Size, Requests}`, около 40 строк в `load.Run`; `lab`, `verifier`,
  `Env`, веб не меняются. Сюжет кладёт залп только в `Rise.Load`, поэтому тихая часть без залпов.
- Состав залпа — отдельный поток ГПСЧ по сиду: фон трёх сюжетов не сдвигается (сверить побитово, как `ids`).
- Каркас обрезает: `Size` ≤ 64, `Every` ≥ 1 с; семафор `maxInflight` общий.
- Алерт по доле ошибок залпы видит, по p95 — нет (медиана посекундных p95).
- Тесты: `TestBurstIsConcurrent`, `TestBurstKeepsBackgroundPlan`, `TestBurstIsCapped` на поддельном транспорте,
  проверка `Burst` в `TestContract`. Нового e2e-теста контракта не нужно.
- ADR 0010. До e2e сюжета — один замер на виртуалке: `Size`, `Every`, фон, алерт за 4 мин без лавины.
- Попутно: у `RatePerSec` нет потолка, при rate > 1e9 `NewTicker` паникует (`load.go:313`).

## Второй проход incident-engineer и решения пользователя, 09.11

e2e до прохода: 15 случаев зелёные три прогона подряд, алерт 1:11. Находки и что сделано:

- **Сортировка только в `createOrder` проходила всё:** залп повторял заказы, которые проверка сама создала
  через API. Встречная пара 30001/30002 теперь лежит в образе, залп повторяет её. Случаи «сортировка в
  createOrder» (ложная) и «сортировка в createOrder и выборке» (верная).
- **Признак провала залпа** (решение пользователя): дедлоки, дыры в номерах заказов из ответов (последовательность
  не откатывается), обновления строк товаров сверх 3 × успешных заказов (`n_tup_upd` считает и откаченные
  попытки — проверено случаем «lock_timeout и точка сохранения»). Откаты только выбирают подсказку: верное
  решение с `Rollback` read-only транзакции и `LOCK TABLE` больше не отвергается.
- **Пауза перед чтением счётчиков 11 с:** простаивающее соединение PG 15+ сбрасывает статистику раз в 10 с.
- **`db-counters`:** `psql -X` и `pg_catalog`. От root в терминале полностью не защититься (ADR 0002, 0004).
- **Новые случаи:** пул на 1 и мьютекс под распродажей (`Repair.AfterAlert`, решение пользователя),
  advisory-блокировка, заглушка повтора, «чтение и запись остатка», `deadlock_timeout` на час (подсказка
  `hintStuck`), `lock_timeout` с точкой сохранения.
- `SERIALIZABLE` не берём: подсказка зависит от того, что случится раньше, дедлок или ошибка сериализации.
