## Что понял за сессию
- Равномерная нагрузка у дедлока даёт либо ноль, либо лавину: фазовый переход. Устойчивые волны дают только залпы (ADR 0010).
- Проверка залпа по откатам отвергала верные починки (`Rollback` read-only транзакции). Признак лишней работы — дыры в номерах заказов (последовательность не откатывается) и `n_tup_upd` сверх нормы: он считает и откаченные попытки, в том числе откат до точки сохранения. Статистику простаивающее соединение PG 15+ сбрасывает раз в 10 с.
- Ложные починки ловят ошибки самих проверок: сортировка только в `createOrder` проходила, пока залп повторял заказы, созданные через API (нужна встречная пара в образе); общий товар-напарник в «последней единице» выстраивал покупателей в очередь и прятал гонку.
- После провала одного случая гонять один случай (`e2e.sh case`), а не весь сюжет: сегодня дважды ушло по 16 минут впустую.
- `udevadm trigger` асинхронный: без `udevadm settle` проверка прав на `/dev/kvm` в CI падала. Раннер медленнее ноутбука примерно на четверть (контракт 5:51 против 4:09).
- Под `set -e` строка `[[ условие ]] && x=1` с ложным условием завершает скрипт, если стоит последней в ветке `case`: `e2e.sh plan` молча ничего не печатал. Писать `if …; then …; fi`.
- Параллельные виртуалки на ноутбуке исключены: машина виснет. Масштаб e2e решается только числом случаев или чужими машинами.
- busybox `kill -l N` для незнакомого номера печатает сам номер, а не пустоту и не ошибку: код 200 выглядел бы как «сигнал 72». Сигналов в Linux 64, поэтому сигнал — только код 129–192.
- Процесс, который завершается, уже вышел из `cgroup.procs`, но ещё виден в `/proc` и `pidof`. Сверка «каждый процесс в cgroup» при частых рестартах давала «вне cgroup» в 2 из 150 чтений даже после ожидания процесса; лечится повтором через 0,1 с. Держит `TestServiceCgroup`.
- `/debug/pprof/` и `/debug/pprof/?debug=1` — HTML, в терминале нечитаемы; профили с `?debug=1` читаются. В брифинге адрес без `curl` пользователь ввёл как команду.
- У `memory.max` ядро может не убивать, а пробуксовывать: вытесняет и подчитывает с диска страницы кода сервиса, `max` в `memory.events` растёт, `oom` = 0, запросы по 8–12 с. Замер на простой программе этого не показал: там почти не исполнялся код. Лечение — бинарник в tmpfs (`lab-service-run`), см. ADR 0007.
- Подсказки при провале проверяются в e2e подстрокой: «перезапускался» совпадало и с «не перезапускался». Метка должна быть уникальной для одной подсказки.
